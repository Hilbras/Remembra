# V5.4.0 Implementation Plan: Developer Platform

## Baseline and Dependency Boundary

V5.0.3 is released and verified. V5.1–V5.3 are not complete in this branch;
therefore V5.4 work must remain additive and must not assume distributed
quotas, distributed jobs, or a new retrieval engine. Existing V4.9/V5.0.3
authentication, tenant, provider, storage, and recovery contracts remain
authoritative.

The V5.1 audit found that rate-limiter, health, metrics, logging, and shutdown
interfaces are still coupled legacy implementations. V5.4 therefore must not
claim distributed quotas, provider-health infrastructure, or lifecycle
coordination until those phases are completed; its SDK/API work remains
additive and usable on the V5.0.3 baseline.

## Overview

V5.4 makes Remembra straightforward to integrate through explicit API
versions, strongly typed SDKs, safe batch contracts, signed webhooks, and
reproducible developer documentation. It does not introduce V5.5 RBAC or V6
runtime changes.

## Architecture Decisions

- Keep existing `/api/v1` and legacy routes backward compatible; add explicit
  version metadata before any future `/v2` contract.
- Keep SDK authentication server-side and never accept tenant identity from
  request payloads as an authority.
- Normalize transport errors into typed SDK errors without exposing provider
  secrets or raw server diagnostics.
- Make retries bounded, idempotency-aware, timeout-aware, and cancellable.
- Sign webhooks with HMAC, validate timestamps, and reject replayed deliveries.
- Treat batch limits, partial outcomes, and transaction policy as explicit
  response metadata; never silently report partial success as full success.
- Treat V5.1–V5.3 unfinished work as a documented limitation, not a reason to
  weaken V5.0.3 guarantees.

## Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Skipped V5.1–V5.3 work leaks into SDK assumptions | High | Keep additive contracts and document unsupported distributed capabilities |
| Retries duplicate writes | Critical | Require idempotency keys for unsafe operations and test replay |
| SDK errors leak provider/server details | High | Single normalized public error model and adversarial tests |
| Webhook replay or signature bypass | Critical | HMAC, timestamp window, nonce/event ID replay store, bounded retries |
| Version drift breaks legacy clients | High | Additive `/api/v1`, contract tests, explicit migration notes |
| Python/Node packages diverge | Medium | Shared endpoint fixtures and parity matrix |
