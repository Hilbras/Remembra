# V5.6.0 Implementation Plan: Distributed Remembra

Roadmap §25–§30, renumbered from V5.2.0/V5.2.1 (see the renumbering banner in
`REMEMBRA_V5_TO_V6_ROADMAP.md`).

## Baseline

V5.5.0 is published at `27e4e11` and V5.5.1 at `c3334b8`. Gates pass on Node
18.20.8 and 24.21.0 with 694 suite, 142 security, 52 recovery, 28 Python, and 42
documentation checks, 0 audit findings. This milestone starts from a tree that
also carries the S1 compare-and-swap fix, which is the prerequisite everything
else depends on: a shared-store implementation is pointless while two writers can
silently lose an update.

## The constraint that shapes everything

Roadmap §26: *"Redis must not become a mandatory dependency for local
installations unless explicitly configured."*

Today the package has four runtime dependencies (`@modelcontextprotocol/sdk`,
`better-sqlite3`, `yaml`, `zod`) and the Python SDK has none. This milestone
adds **no fifth**. The Redis client is reached through a dynamic `import()` that
only executes when `REMEMBRA_REDIS_URL` is set, and the package itself lives in
`devDependencies` plus `peerDependenciesMeta.optional`. So:

| Deployment | Behaviour |
|---|---|
| No `REMEMBRA_REDIS_URL` | exactly today's single-host behaviour, and `redis` is never imported |
| URL set, `redis` installed | shared state across instances |
| URL set, `redis` missing | startup fails with a named, actionable error — never a silent fallback to local state, which would look like it worked while running split-brain |

That last row matters more than it looks. A shared-state layer that quietly
degrades to per-instance state is worse than no shared-state layer, because
every cross-instance invariant silently stops holding.

## Architecture decisions

- **Interfaces before adapters.** A shared lock, a shared job store, and a shared
  rate limiter are defined as interfaces with in-process implementations that are
  the current code. Redis is an adapter over them, not a dependency of them.
- **Check-then-act is not a decision.** S1 was exactly this. Every cross-instance
  mutation is a single atomic operation — a compare-and-swap, a conditional
  update, or a transactional claim — and the tests use two real instances rather
  than mocks.
- **Leases, not locks, for work.** A distributed lock held across a crash is a
  deadlock. Every cross-instance claim carries an owner and an expiry, is
  renewable, and is reclaimable when it ages out.
- **Tenant isolation is the thing being preserved.** §30 asks for a guarantee
  that distributed execution does not weaken it. Concretely: identity stays an
  opaque truncated digest, authentication still precedes every charge, and no
  shared-state key is ever built from a raw principal.
- **Idempotency is the safety net.** Anything a worker may run twice must be safe
  to run twice, because §30 explicitly tests duplicate execution.
- **Bounded everything.** In-process state is capped (the S1-era limiter work set
  the precedent), payloads are size-capped, and every poll interval is bounded.
- **One process still needs no configuration.** The default deployment shape
  stays "run it and it works".

## Task list

### Phase 0: Audit

- [x] **T01 — Audit the single-host assumptions.**
  - Acceptance: every in-process and durable state that N instances would
    duplicate or contend for is recorded, with the concurrency contract in
    `src/backend.ts` checked against each mutating path.
  - Verification: reproduction with two backend instances over one database.
  - Outcome: [`docs/v5.6.0-audit.md`](../docs/v5.6.0-audit.md) — S1 (fixed, a
    silent cross-instance lost update), S2 (four more read-modify-write mutators
    with no CAS), S3 (per-server readiness cache), S4 (in-process state N would
    duplicate), S5 (durable state N would contend for, three of unknown safety),
    S6 (the file backend's lock is a pid file: same-host only).

### Phase 1: Cross-instance primitives, no Redis

- [x] **T02 — Introduce a `LockProvider` interface with leases.**
  - Acceptance: `acquire`, `renew`, `release` with owner, lease expiry, and
    reclamation of an aged-out lease; an in-process implementation that is what
    runs today, and a file-backed implementation with a real cross-process
    story. Closes audit S6's design question for one host.
  - Verification: two providers contending; lease expiry reclaimed by a peer;
    renewal prevents reclamation; release by a non-owner refused.
  - Depends on: T01.
  - Scope: M.
  - Outcome: `src/lock.ts` adds `LockProvider`/`LockHandle`, `InProcessLockProvider`
    and `FileLockProvider`, `lockKey` (opaque by construction), and `withLock`.
    Every acquisition is a lease with an owner and an absolute expiry, so a
    crashed holder is reclaimed rather than deadlocking. Two rules are enforced
    and tested: `release()` is owner-checked so it can never clear a peer's
    lease, and `renew()` returns `false` once a lease is lost, so a partitioned
    worker cannot resume writing. 15 tests. Two of them caught defects in this
    implementation: an unreadable lease file livelocked `acquire` forever, and
    `isHeld()` never observed the file it had created.

- [x] **T03 — Add a durable job ledger with the §27 job model.**
  - Acceptance: `queued`/`running`/`completed`/`failed`/`retrying`/`cancelled`
    with `jobId`, `tenantId`, `type`, `payload`, `createdAt`, `startedAt`,
    `completedAt`, `attempt`, `maxAttempts`, `lease`; claims are atomic
    compare-and-swap so exactly one worker can hold a job; a `JobStore`
    interface with in-memory and SQLite implementations.
  - Verification: two claimers, one winner; lease expiry makes a job claimable
    again; a completed job is never re-claimed; payload and tenant are bounded.
  - Depends on: T02.
  - Scope: L.
  - Outcome: `src/job-store.ts` adds `JobStore` with `InMemoryJobStore` and
    `SqliteJobStore`, published as `@hilbras/remembra/job-store`. All six §27
    states and all ten fields are carried. A claim is a single
    `UPDATE ... RETURNING`, so the database picks the winner and returns the row
    it actually claimed — never a read-then-write, which is the S1 shape. Every
    behavioural test runs against both implementations so they cannot drift, plus
    two cross-connection tests. 28 tests.

- [ ] **T04 — Run the existing job queue on the durable ledger.**
  - Acceptance: `JobQueue` takes a `JobStore`; the single-host default is the
    in-memory store so nothing changes for one process; durable mode survives a
    worker restart and does not run a job twice concurrently.
  - Verification: restart mid-job is reclaimed after lease expiry; a duplicated
    delivery is a no-op; audit S4's duplication of maintenance/decay/consolidation
    is addressed for the durable path.
  - Depends on: T03.
  - Scope: L.

### Phase 2: Shared state (optional)

- [ ] **T05 — Add the Redis adapter behind the existing interfaces.**
  - Acceptance: `RedisRateLimiter` implements the T02 `RateLimiter` interface and
    the quota contract; `RedisLockProvider` implements T02's; both reached only
    through a dynamic `import()` of an optional peer. `redis` is never a
    `dependencies` entry.
  - Verification: absent `REMEMBRA_REDIS_URL` imports nothing; URL set without
    the package fails startup with a named error; two processes share one budget
    and one lock through the adapter.
  - Depends on: T04.
  - Scope: L.

- [ ] **T06 — Configuration, capability reporting, and honest degradation.**
  - Acceptance: `REMEMBRA_REDIS_URL` validated at startup; the capability manifest
    advertises the *build* (so `distributed` is present whether or not Redis is
    configured, exactly as `webhooks` already is); `/health/ready` reports whether
    shared state is actually connected, without leaking the URL or credentials.
  - Verification: capability parity test; health reports connected/absent
    distinctly; an unreachable Redis is reported, never silently ignored.
  - Depends on: T05.
  - Scope: M.

### Phase 3: Process shape

- [ ] **T07 — Separate server, worker, and scheduler entry points.**
  - Acceptance: §28's split, with the default still a single process running
    everything. `remembra serve`, `remembra worker`, `remembra scheduler`, and
    no configuration needed for the one-process case.
  - Verification: one process still serves and drains webhooks; a worker-only
    process refuses HTTP duties and vice versa; no port or token is required in
    single-process mode.
  - Depends on: T04.
  - Scope: M.

### Phase 4: Adversarial verification

- [ ] **T08 — Run the §30 failure matrix.**
  - Acceptance: duplicate job execution, expired leases, worker crash, Redis
    restart, network partition, stale cache, concurrent writes, concurrent
    restore, and concurrent migration are each tested with two *real* instances,
    and each asserts a stated invariant rather than merely "did not crash".
    Tenant isolation is asserted across every shared-state key.
  - Verification: a dedicated matrix, green on both runtimes.
  - Depends on: T05, T07.
  - Scope: L, split into focused slices.

## Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| A required Redis breaks the Node 18 gate and the zero-dependency character | Critical | Optional peer, dynamic import, per the constraint above; T05 and T06 test the absent case first |
| Shared state silently degrades to local, running split-brain | Critical | URL set without a working client is a startup failure, never a fallback; health reports the difference |
| A distributed lock deadlocks a crashed holder | High | Leases with expiry and renewal, never a held lock; reclaimed by a peer |
| A job runs twice | High | Atomic claim plus idempotent handlers; T08 tests duplicate delivery explicitly |
| Audit S1-style check-then-act reappears in new code | High | Every cross-instance mutation is atomic; tests use two real instances, not mocks |
| Cross-instance keys leak a tenant | Critical | Keys are built from the same truncated digests as rate identity; a test asserts no raw principal reaches shared state |
| Per-instance state silently becomes N × the configured limit | High | T05's shared limiter, and a startup warning when `REMEMBRA_RATE_LIMIT` is set with per-instance limiting in a multi-process deployment |

## Open questions

- Should the shared rate limiter be the default when `REMEMBRA_REDIS_URL` is set,
  or opt-in per dimension? Default: replace the in-process limiter wholesale, so
  a deployment cannot accidentally run half-shared quotas.
- Does the worker need its own authentication, or is "reaching the store" the
  trust boundary? Default: no new credential; the store's own durability and
  tenant scoping are the boundary, since adding a worker token would create a
  second secret to leak for no isolation gain.
