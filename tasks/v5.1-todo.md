## Phase 1: Rate and quota foundations

- [x] **V5.1-T02 — Add RateLimiter abstraction**
  - Acceptance: `check`, `consume`, and `reset` are async, typed, bounded, and
    injectable; current authentication-before-rate-limit behavior and legacy
    callers remain compatible.
  - Verify: focused identity/window/reset tests plus SEC-RL/SEC-AUTH regressions.
  - Depends on: V5.1-T01.
  - Progress: complete. The request path now depends on the `RateLimiter`
    interface, injected via `HttpOptions.rateLimiter`, with
    `InProcessRateLimiter` as the shipped implementation — so V5.2 can supply a
    shared-store limiter without editing `http.ts`. `check` and `consume` are
    distinct, so a speculative check no longer spends quota. State is bounded:
    a `maxIdentities` ceiling plus a deterministic expiry sweep and LRU
    eviction replaced the old `Math.random()` pruning, and the audit's
    50,001-entry reproduction is now 10,000 (40,000 evicted).
    `rateLimitIdentity` rejects any value that is not a hex digest, so a raw
    principal or API key fails loudly instead of becoming a quota key. Tenant
    dimensions are named (`organization=`, `user=`, …) and stay hashed.
    22 new tests: `RL-001`–`RL-009` unit and `RL-HTTP-001`–`RL-HTTP-006`
    parity. SEC-RL-001 and SEC-RL-002 pass unchanged, and
    `REMEMBRA_RATE_LIMIT` / `REMEMBRA_RATE_WINDOW_MS` still configure the
    default limiter.

- [x] **V5.1-T03 — Define distributed-ready quota contract**
  - Acceptance: global, organization, project, user, agent, API-key, IP,
    endpoint, and provider dimensions have typed policies and precedence;
    absent trusted dimensions cannot widen a quota identity.
  - Verify: quota matrix, bypass tests, and configuration validation.
  - Depends on: V5.1-T02.
  - Progress: complete. `src/quota.ts` defines `QuotaPolicy`, `QuotaPolicies`,
  `parseQuotaPolicies` for `REMEMBRA_QUOTAS`, and `QuotaRateLimiter`, which
  composes one bounded `InProcessRateLimiter` per dimension so the ceiling
  cannot multiply. Precedence is the declared `RATE_LIMIT_DIMENSIONS` order with
  the base budget last, so the same exhausted state always reports the same
  dimension; a 429 can now be attributed rather than being anonymous.
  Charging is all-or-nothing, so a request denied by one dimension is not
  charged to the others. Two rules keep it fail-closed: the base per-identity
  budget is charged for every request, so adding a policy can only make a
  deployment stricter, and a dimension is charged only when the request carries
  a trusted value for it — an absent dimension falls back to the base budget
  rather than escaping it. `QUOTA-006b` pins that a request missing all eight
  configured dimensions is charged once, not nine times, which is a bug the
  first implementation had. 20 tests: `QUOTA-001`–`QUOTA-015` and
  `CONFIG-001`–`CONFIG-004`, covering the nine-dimension matrix, ten distinct
  configuration failures that each name the variable and the entry, and
  all-or-nothing charging.

## Phase 2: Health and observability

- [x] **V5.1-T04 — Separate health APIs**
  - Acceptance: preserve `/health`; add bounded `/health/live`,
    `/health/ready`, `/health/storage`, and `/health/provider` contracts with
    explicit authentication and no secret/memory disclosure.
  - Verify: route/status/state/fallback/redaction tests.
  - Depends on: V5.1-T01.
  - Progress: complete. `/health/live` is public and cheap — process state only,
    no storage read and no durable write — so it reports `200` even when
    storage is broken, and reports `draining: true` once `beginShutdown()` is
    called so an orchestrator can take the instance out of rotation.
    `/health/ready`, `/health/storage`, and `/health/provider` are handled after
    authentication and rate limiting, so they inherit the existing rules
    without duplicating any auth code. `/health` keeps its exact response shape
    and status codes; the audit's concern that an unauthenticated caller could
    drive a storage read and a recovery-state write per request is addressed with
    a short cache plus single-flight, verified by counting backend scans: 25
    sequential probes cost one scan, 20 concurrent probes cost one scan, and
    `REMEMBRA_HEALTH_CACHE_MS=0` restores a live answer per probe. Failures are
    cached too, so a broken disk is not hammered. No health response carries
    memory content, a storage path, an error message, or a provider key —
    `HEALTH-002`, `HEALTH-007`, and `HEALTH-008` assert the negatives. The
    route-parity test caught the three new authenticated routes as
    undocumented, so `docs/openapi.yaml` gained the paths plus `StorageHealth`
    and `ProviderHealth` schemas. 15 tests: `HEALTH-001`–`HEALTH-014`.

- [x] **V5.1-T05 — Complete production metrics**
  - Acceptance: request, rate-limit, memory, provider, storage, snapshot, and
    recovery metrics use bounded labels and expose p50/p95/p99 where useful.
  - Verify: exposition, reset isolation, and cardinality tests.
  - Depends on: V5.1-T01, V5.1-T04.
  - Progress: complete. `MetricsRegistry` gained `quantile`, `summary`, `names`,
  and `seriesCount`; quantiles interpolate inside the bucket they fall in and
  report 0 for an unobserved series rather than a fabricated latency. The six
  §21 series the audit found missing are declared and recorded, including
  `remembra_rate_limit_hits_total{dimension}`, which the T03 quota contract made
  possible — a 429 can now name the budget that refused it.
  Audit finding **M4** was the substantive one: seven *further* series were
  declared and never written by anything at all, so a dashboard on them rendered
  empty and looked like data loss. The four provider and storage series now have
  a real choke point — `observeProviderCall` in `embeddings.ts`, used by both
  `embedText` and `llm.chat`, plus a timer around the backend store — and a
  failing call is counted by classified code and rethrown unchanged. The three
  memory-count gauges, three rate gauges, the cost gauge, and
  `remembra_token_usage_total` were **removed** rather than left empty: each
  needs a full backend scan, a quality computation, or usage the adapter
  contract does not report, and a series that can never report is a worse lie
  than an absent one. `JobType` labels are bounded to a closed set, and M3's own
  test caught that bounding only the completion site was not enough — the
  enqueue-time increment was the one creating a series per host-defined job
  type, and it is bounded now. 15 tests: `METRIC-001`–`METRIC-015`, including
  exposition well-formedness, percentile ordering, reset isolation, and
  cardinality bounds.

- [x] **V5.1-T06 — Standardize structured request logging**
  - Acceptance: request/operation metadata uses centralized redaction; raw
    queries, secrets, and unbounded tenant values never enter logs.
  - Verify: structured schema and adversarial log tests.
  - Depends on: V5.1-T01.
  - Progress: complete. The audit's L1/L2 finding is closed: `logEvent` now
    merges an `AsyncLocalStorage` request context, so every line carries
    `requestId`, `operation`, hashed `tenantId`/`agentId`, and `durationMs` —
    including lines from the service, storage, provider, and job-queue layers,
    which know nothing about HTTP and would otherwise have to thread the context
    by hand. Contexts nest, an explicit field overrides the context, and
    `LOG-016` pins that concurrent requests never observe each other's context.
    A field policy enforces §22's exclusions structurally, because redacting by
    field *name* cannot tell that `query` holds user text: content and path
    fields are dropped unless `REMEMBRA_DEBUG` is set, and identity fields are
    replaced by a short stable digest so correlation survives without a raw
    tenant or user identifier reaching every log aggregator and backup.
    **Two pre-existing leaks were fixed.** `retrieval.debug` logged the raw
    query text behind `REMEMBRA_DEBUG_RETRIEVAL=1` rather than the documented
    `REMEMBRA_DEBUG`, so enabling a debug trace was enough to put user text in a
    log; and `migration_start` logged a storage path unconditionally. `LOG-006`
    pins that no other debug flag unlocks a data dump while the documented
    opt-in still works. One `http.request` completion line per request carries
    the bounded route slug, method, status, and duration — never the raw path.
    16 tests: `LOG-001`–`LOG-016`, weighted towards the negative cases.

## Phase 3: Lifecycle and hardening

- [x] **V5.1-T07 — Implement bounded graceful shutdown**
  - Acceptance: stop intake, drain active work with a deadline, stop jobs,
    flush observability, and close providers/storage without hanging.
  - Verify: in-flight, timeout, repeated-signal, and cleanup tests.
  - Depends on: V5.1-T04, V5.1-T05, V5.1-T06.
  - Progress: complete. `src/shutdown.ts` adds `ShutdownCoordinator` and
    `registerStandardShutdownPhases`, running §23's sequence in dependency order:
    mark draining → stop accepting → stop background work → drain webhooks →
    stop jobs → close providers → close storage. The audit's S1–S5 are all
    addressed. **Bounded:** one deadline (`REMEMBRA_SHUTDOWN_TIMEOUT_MS`,
    default 10s) covers the whole sequence rather than each phase, a wedged phase
    is reported `timeout` with the phases after it `skipped`, and storage is
    never closed while a phase may still be in flight. **Idempotent:** a second
    signal joins the in-flight shutdown and shortens the deadline to 1s, so a
    second Ctrl-C exits promptly. **Honest:** a forced shutdown exits `1`, which
    the old always-`exit(0)` handler could not express. Wiring: `startWebhookDrain`
    now returns a stop function, `closeProviders` and `backendForShutdown` were
    added to the service, and **MCP mode now installs signal handlers at all** —
    previously an MCP server took the default `SIGTERM` disposition and died
    with no drain and no recovery-state flush. Two series and a
    `shutdown.complete` line per phase report the outcome. 15 tests
    (`SHUT-001`–`SHUT-015`), all driven from an injected clock: the production
    timer is deliberately `unref`'d so a shutdown deadline can never keep a
    process alive, which on Node 18 left the test file with nothing holding the
    event loop open — a real portability finding, not a test artifact.

- [x] **V5.1-T08 — Add production stress coverage**
  - Acceptance: concurrency, large payload/search, provider timeout storms,
    rate-limit storms, database contention, shutdown/restart under load, and
    resource-leak checks are bounded and reproducible.
  - Verify: dedicated stress matrix on Node 18.20.8 and 24.21.0.
  - Depends on: V5.1-T02–T07.
  - Progress: complete. `src/test/stress.test.ts` covers every scenario §24
    names — 100 and 1K concurrency (both the shed path and the under-cap path),
    large and oversized payloads, large search, a provider timeout storm, a
    rate-limit storm in-process and over HTTP, a quota storm, database
    contention, shutdown under load, restart under load, file-descriptor leaks,
    and metric cardinality. All bounded, with no wall-clock thresholds, so the
    matrix is reproducible on a slow runner; latency budgets stay in the existing
    benchmarks. **It found a real defect.** `QuotaRateLimiter` decided and
    charged with an `await` in between, so every caller in a concurrent burst
    observed the same empty window: a 500-request storm against an organization
    cap of 20 served all 500. A rate limiter that can be bypassed by sending
    requests in parallel is not a rate limiter. Decide-and-charge is now
    serialized (and `reset` with it), pinned by `QUOTA-010b`, `QUOTA-010c`, and
    `QUOTA-010d`. The matrix also corrected two of my own wrong premises rather
    than papering over them: the 40 refused requests in the 100-concurrency case
    were `429` from the default 60/min budget, not the concurrency cap; and a
    14 KB payload "losing" data was the `token` rule of the default
    sensitive-data policy matching hyphen-separated words — a shape judgement,
    not a size limit, now pinned as `STRESS-003b` so it is not rediscovered as
    data loss. 16 tests, green on Node 18.20.8 and 24.21.0.
