# V5.7.0 Implementation Plan: Advanced Retrieval Engine

Roadmap §31–§38. Ships as **5.7.0** per the renumbering settled in the 5.5.0
compatibility report.

The audit ([docs/v5.7.0-audit.md](v5.7.0-audit.md)) found six areas. This plan
sequences them so each step is verifiable when it lands, and so the measurement
that proves the deduplication work exists *before* the deduplication work.

## Baseline

- Published: **5.6.0** (npm), tag `v5.6.0`.
- Gates: 799 suite, 142 security, 52 recovery, 28 Python, 44 documentation
  checks, 0 audit findings, green on Node 18.20.8 and 24.21.0.
- Retrieval today: 659 lines in `src/retrieval.ts`, plus `src/eval.ts`.

## The constraint that shapes everything

**A retrieval change that cannot be measured is not a retrieval change.** §38
requires that every retrieval-engine change run against a benchmark set, and the
audit found that two of the seven required metrics do not exist — including
duplicate rate, which is the metric that would have caught the missing
deduplication automatically.

So the first task is a measurement, not a feature. It is tempting to start with
S1, the substring-matching bug, because it is the most visible defect. Doing that
first means fixing lexical scoring with no way to show it improved anything.

## Architecture decisions

- **Token boundaries, not substring.** A query term matches a whole token. A
  prefix match is a distinct, separately-weighted signal, not a weaker exact
  match — conflating them is what produced the `cat`/`concatenate` collision.
- **Phrases are scored, not filtered.** A phrase match is a bonus over the sum of
  its terms, so a document containing the phrase outranks one containing the same
  words scattered. Filtering would silently drop results.
- **Fields are weighted.** Content, tags, and title are separate fields with
  declared weights. Concatenating them into one string destroyed the information
  §32 asks for.
- **Real IDF needs corpus statistics.** The scorer is given per-term document
  frequencies. This changes its signature, so S1 and S2 are one task.
- **Deduplication is detection, not diversity.** MMR stays as a diversity
  reordering and stops pretending to be a dedup pass. Exact, same-source, and
  superseded detection are separate, deterministic, and testable.
- **Deduplication suppresses results; it never deletes records.** §36 forbids
  destroying history. A superseded memory is excluded from default results and
  remains retrievable and readable.
- **The budget is one object.** `maxTokens`, `maxItems`, `maxBytes`, and
  `maxLatency` are fields of a single budget, because expressing "fit this in
  8k tokens and 16KB and 200ms" as three independent parameters is how a caller
  ends up satisfying two and violating the third.
- **Exceeding `maxLatency` returns the best results so far.** Not an error. A
  memory system that returns nothing under load is worse than one that returns
  good-enough results, and the caller can see the truncation.

    accordingly. A term rare in the corpus outranks an equally-covered common
    term. The coverage discount in S2 is replaced, not layered on.
  - Verification: two documents covering the same fraction of the query score
    differently when the shared term differs in corpus rarity; the
    all-terms-beats-one-term ordering from the audit is preserved.
  - Depends on: T02.
  - Scope: M.

### Phase 2: Deduplication

- [ ] **T04 — Exact and same-source duplicate detection.**
  - Acceptance: exact duplicates are detected by normalized content, not by
    embedding similarity, so they are caught with embeddings off. Same-source
    duplicates are grouped by provenance source. Both suppress results and delete
    nothing.
  - Verification: identical text is collapsed in the **default**
    (`embeddingProvider: none`) configuration, which is where the audit found it
    silently passing through. Duplicate rate from T01 drops.
  - Depends on: T01.
  - Scope: M.
- [ ] **T05 — Superseded-memory suppression.**
  - Acceptance: a memory with `supersededBy` set is excluded from default results
    and retrievable via an explicit flag. Retrieval never deletes it.
  - Verification: the audit's `supersededBy` reproduction now returns only the
    superseding memory by default, and both when the flag is set.
  - Depends on: T04.
  - Scope: S.
  - Open: confirm the default-suppression decision (audit open question 1).

### Phase 3: Budget and weights

- [ ] **T06 — One context budget object.**
  - Acceptance: `maxTokens`, `maxItems`, `maxBytes`, and `maxLatency` are fields
    of one budget. Exceeding the latency budget returns the best results so far
    with a flag saying so, rather than an error.
  - Verification: a budget with all four bounds is honoured simultaneously; each
    bound alone is tested; a slow provider degrades to partial results instead of
    failing.
  - Depends on: T04.
  - Scope: M.
  - Open: confirm the degrade-rather-than-fail decision (audit open question 3).
- [ ] **T07 — Configurable fusion weights.**
  - Acceptance: the lexical, semantic, metadata, recency, and confidence weights
  from §34 are configurable, with the current values as defaults so no existing
  behaviour changes.
  - Verification: a deployment that weights lexical above semantic gets a
  measurably different ranking on the benchmark set, and the defaults reproduce
    today's ranking.
  - Depends on: T03.
  - Scope: S.

### Phase 4: Guardrail

- [ ] **T08 — Enforce the benchmark gate.**
  - Acceptance: every retrieval change runs the benchmark set, and the gate fails
    on a regression in precision, recall, MRR, nDCG, duplicate rate, or latency
    percentile. §38's rule becomes mechanical rather than aspirational.
  - Verification: a deliberately degraded ranking fails the gate.
  - Depends on: T01, T02, T04.
  - Scope: M.

## Open questions to settle before coding

1. **Suppress superseded memories by default?** T05 assumes yes, with an explicit
   `includeSuperseded` escape hatch. Returning v1 when v2 supersedes it is usually
   wrong, but §36 only forbids *destroying* history, which is about storage rather
   than retrieval. I would not want to settle this in code alone.
2. **What is §32's "metadata filters"?** Filters inside the lexical scorer, or the
   existing `scope`/`type` filters promoted into a declared filter object? The
   roadmap lists it under lexical retrieval, which points at the former, but the
   existing surface already covers most of the latter.
3. **Exceeding `maxLatency`: partial results or error?** T06 assumes partial
   results with a flag. For a memory system, returning nothing under load is
   worse than returning good-enough results — but it should be a stated decision
   rather than an implementation detail.

## Checkpoints

- [ ] After T01: both new metrics can fail on a deliberately broken input.
- [ ] After T03: a query matching more terms still outranks one matching fewer,
  and corpus rarity now moves the score.
- [ ] After T05: returning v1 and v2 of a superseded policy is no longer the
  default, and nothing was deleted.
- [ ] After T08: a retrieval regression cannot reach a release.

## Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Lexical scoring changes reorder existing results for current users | High | Defaults reproduce today's behaviour; the benchmark gate measures the delta before it ships |
| Deduplication hides a memory the user wanted | Medium | Suppression is a result-set decision, not a deletion; superseded copies stay retrievable behind a flag |
| Real IDF needs corpus statistics the caller does not have | Medium | Computed from the candidate set, bounded, and falling back to the current behaviour when statistics are unavailable |
| A latency budget silently truncates results | Medium | Truncation is reported in the result, never silent |
| Two new metrics pass no matter what | High | T01's acceptance requires each metric to fail on a deliberately broken input |

## What this milestone will not claim

- **No change to a single-process deployment's behaviour** beyond retrieval
  quality. No new dependency, no new required configuration, no change to the
  HTTP contract except additive optional budget fields.
- **Not a full vector-index replacement.** The brute-force cosine path stays; this
  milestone makes ranking and selection correct, not asymptotically faster. That
  is §52–§58's slot.
