# V5.7.0 Implementation Plan: Advanced Retrieval Engine

Roadmap §31–§38. Ships as **5.7.0** per the renumbering settled in the 5.5.0
compatibility report.

The audit ([docs/v5.7.0-audit.md](v5.7.0-audit.md)) found six areas. This plan
sequences them so each step is verifiable when it lands, and so the measurement
that proves the deduplication work exists *before* the deduplication work.

## Baseline

- Published: **5.6.0** (npm), tag `v5.6.0`.
- Gates: 799 suite, 142 security, 52 recovery, 28 Python, 44 documentation
  checks, 0 audit findings, green on Node 18.20.8 and 24.21.0.
- Retrieval today: 659 lines in `src/retrieval.ts`, plus `src/eval.ts`.

## The constraint that shapes everything

**A retrieval change that cannot be measured is not a retrieval change.** §38
requires that every retrieval-engine change run against a benchmark set, and the
audit found that two of the seven required metrics do not exist — including
duplicate rate, which is the metric that would have caught the missing
deduplication automatically.

So the first task is a measurement, not a feature. It is tempting to start with
S1, the substring-matching bug, because it is the most visible defect. Doing that
first means fixing lexical scoring with no way to show it improved anything.

## Architecture decisions

- **Token boundaries, not substring.** A query term matches a whole token. A
  prefix match is a distinct, separately-weighted signal, not a weaker exact
  match — conflating them is what produced the `cat`/`concatenate` collision.
- **Phrases are scored, not filtered.** A phrase match is a bonus over the sum of
  its terms, so a document containing the phrase outranks one containing the same
  words scattered. Filtering would silently drop results.
- **Fields are weighted.** Content, tags, and title are separate fields with
  declared weights. Concatenating them into one string destroyed the information
  §32 asks for.
- **Real IDF needs corpus statistics.** The scorer is given per-term document
  frequencies. This changes its signature, so S1 and S2 are one task.
- **Deduplication is detection, not diversity.** MMR stays as a diversity
  reordering and stops pretending to be a dedup pass. Exact, same-source, and
  superseded detection are separate, deterministic, and testable.
- **Deduplication suppresses results; it never deletes records.** §36 forbids
  destroying history. A superseded memory is excluded from default results and
  remains retrievable and readable.
- **The budget is one object.** `maxTokens`, `maxItems`, `maxBytes`, and
  `maxLatency` are fields of a single budget, because expressing "fit this in
  8k tokens and 16KB and 200ms" as three independent parameters is how a caller
  ends up satisfying two and violating the third.
- **Exceeding `maxLatency` returns the best results so far.** Not an error. A
  memory system that returns nothing under load is worse than one that returns
  good-enough results, and the caller can see the truncation.

## Task list

### Phase 0: Measurement

- [x] **T01 — Add the two missing evaluation metrics.**
  - Outcome: `src/eval.ts` now reports **token efficiency** (tokens belonging to
    relevant results, over total tokens returned) and **duplicate rate** (returned
    results repeating an earlier one), per query and in the aggregate, with raw
    counts alongside. `duplicateKey`/`isExactDuplicate` added to `retrieval.ts` so
    the metric and the future detector share one function. 12 tests.
    Token counting defaults to the same `defaultTokenCounter` the context assembler
    uses, so the number means the same thing here as when the memories are actually
    handed to a model.
  - The aggregate rate is a **mean of ratios** while the counts are sums, so
    `duplicates / returned` is not the rate when result counts vary. Both are
    reported, the distinction is documented on the type, and T01-011 pins a case
    where the two genuinely disagree.
  - A metric that cannot fail is not a metric, so each is checked against a
    deliberately broken input. Verified by mutation: hardcoding duplicate rate to 0
    fails 8 tests, and making token efficiency count results instead of tokens
    fails 8. A real metric/detector divergence — the detector stripping trailing
    punctuation and the metric not — fails T01-003. My first divergence mutant was
    a no-op (`.toUpperCase().toLowerCase()` is identity) and caught nothing, which
    is why the second attempt used a genuine one.
  - Acceptance: `src/eval.ts` reports token efficiency (tokens returned per unit
    of context budget consumed) and duplicate rate (fraction of returned results
    that are duplicates). Both appear in the aggregate, not only per query.
  - Verification: a deliberately duplicated benchmark set reports a non-zero
    duplicate rate; a set with no duplicates reports zero. A metric that cannot
    fail is not a metric.
  - Depends on: nothing.
  - Scope: S.

### Phase 1: Lexical correctness

- [x] **T02 — Token boundaries, phrases, and field weights.**
  - Outcome: `keywordScore` rewritten with a `tokenize` step, whole-token matching,
    a separately-weighted prefix signal, a scored phrase bonus, and independent
    `content`/`tags` weights (`LexicalWeights`, frozen defaults). CJK is tokenized
    per character. 16 tests, each a row of the audit's reproduction table. Scale
    still capped at 60 and a zero score still means zero, so the `keyword_hit`
    explanation flag stays honest.
  - **Two structural flaws found in my own normalisation**, both making the new
    weights unobservable, which is worse than not having them:
    1. Leaving the phrase bonus out of the denominator let coverage exceed 1, so
       the 60 cap saturated and flattened the phrase and field distinctions —
       `"the red car"` and `"car the red"` both scored 60.00.
    2. Putting `phrase` into the denominator fixed the saturation but made the
       weight *mathematically inert*: numerator and denominator scaled together, so
       phrase = 1, 1.5, 2 and 3 all scored identically. A weight nobody can move is
       not a configurable weight.
    The denominator is now a fixed headroom constant, so every weight moves the
    score (phrase 1/1.5/2 → 30/45/60) and default-weight cases stay below the cap.
  - `content` is deliberately the **unit** the other weights are measured against,
    so scaling it is a no-op by construction. Documented on the field and pinned in
    T02-012, so a later reader does not assume it is tunable and chase a bug that
    is not there.
  - Verified by mutation: reverting to substring matching fails 10 tests, dropping
    the phrase bonus fails 6, folding tags into content fails 6, and making prefix
    credit equal to exact fails 2.
  - `score()` still uses the old `keywordScoreV1` on purpose — it is kept for the
    phase4 regression harness — so substring behaviour remains on that test-only
    path by design. Worth knowing before someone greps for it.
  - 4 of my own premises were wrong. The instructive one: I expected the audit's
    `cat`/`concatenate` row to be a *prefix* collision and wrote a test demanding a
    positive prefix score. It is mid-word — `"concatenate".startsWith("cat")` is
    false — so the correct fixed behaviour is 0, and the test was asserting the
    wrong mechanism. The audit now says so.
  - Acceptance: `keywordScore` matches whole tokens; a prefix match is a separate
    weighted signal; a phrase match is a bonus over its terms; content, tags, and
    title are weighted independently. The `cat`/`concatenate` collision is gone.
  - Verification: the audit's reproduction table becomes a test, including the
    reversed-order and no-phrase cases, and the field-weight inequality.
  - Depends on: T01.
  - Scope: M.
- [x] **T03 — Real inverse document frequency.**
  - Outcome: `buildTermStatistics` and `normalisedIdf` replace the placeholder
    entirely — the scorer's dead `totalDocs` parameter is gone, and each term's
    credit is scaled by a normalised IDF in (0, 1]. Statistics are built once per
    search in `searchQ` using the backend's true corpus total, so a paginated
    candidate set still discounts common terms against the real corpus. 16 tests.
  - **Normalised, not raw, IDF.** Scaling by `log(1 + documentCount) / idf(t)` is
    what keeps the coverage denominator fixed. Raw IDF would rescale every score by
    whichever term happened to be rarest, quietly re-breaking the phrase and field
    distinctions T02 added — the same class of bug T02 already fixed once.
  - A term with **no recorded frequency is discounted as if ubiquitous**, because
    assuming a term is rare when it is common is how a stopword dominates a result
    set. Pinned: it is discounted, not credited with rarity, and *no statistics at
    all* is deliberately a different case (neutral).
  - **A test-design gap I found by mutation and had to close.** My first 13 tests
    all called `keywordScore` with statistics they built themselves, so they
    verified the scorer honoured them and nothing more. Breaking the *call site* —
    never passing the statistics, ignoring the corpus total — failed **none** of
    them. The scorer could have been perfect and the feature entirely
    disconnected. Three end-to-end tests through `searchQ` were added, after which
    the same mutations fail 5 and 3 tests.
  - Verified by mutation: statistics never passed → 5 failures; `totalDocs` ignored
    → 3; unrecorded term treated as rare → 5; rarity flattened to a constant → 15.
    Halving the rarity influence fails **nothing**, because it preserves ordering —
    an honest limit of ratio-based assertions, recorded rather than papered over.
  - **Seven of my own premises were wrong**, several instructive: I asserted the old
    factor was *inverted* (it was not — coverage ordering was already correct);
    expected an unrecorded term to be neutral (the intent is to discount it);
    expected an empty corpus to score 0 (with nothing to discount by, neutral is
    right); and had the `totalDocs` comparison **backwards** — ten occurrences in
    10,000 documents is rare, not common. Also: comparing ids across two separate
    `build()` calls, looking up an explanation for a document outside the top-k so
    both reads were 0, and choosing a df=1 term, which is scale-invariant by
    construction and so demonstrated nothing.
  - Acceptance: the scorer is given per-term document frequencies and weights
    accordingly. A term rare in the corpus outranks an equally-covered common
    term. The coverage discount in S2 is replaced, not layered on.
  - Verification: two documents covering the same fraction of the query score
    differently when the shared term differs in corpus rarity; the
    all-terms-beats-one-term ordering from the audit is preserved.
  - Depends on: T02.
  - Scope: M.

### Phase 2: Deduplication

- [x] **T04 — Exact and same-source duplicate detection.**
  - Outcome: `dedupeResults` added to `src/retrieval.ts` and wired into
    `searchQ` ahead of MMR, on the already-sorted list. Detection uses the
    `duplicateKey` T01 put in place, so the metric and the detector cannot diverge.
    Needs **no embeddings**, which is the point: the audit found `mmrDedup` returned
    its input unchanged in the default `embeddingProvider: none` mode. Exact
    collapsing is on by default; same-source is off. `dedupeExact` and
    `dedupeSameSource` are exposed on HTTP search and the MCP `search` tool as
    escape hatches. 15 tests.
  - **Same-source collapsing is off by default, deliberately asymmetric.** Identical
    text from two *different* sources is often corroboration — the same fact
    independently recorded by a conversation and an agent — and collapsing it
    discards the second source, which is a worse error than showing a repeat.
    Identical text from the *same* provenance is treated as a duplicate import.
    Grouping needs provenance finer than `sourceType`, since every hand-written
    memory is `manual`.
  - **This is the first task in the milestone that changes a default**, and it broke
    two existing tests. Both used *identical content* as a convenient way to hold the
    lexical score constant — the reranking-tie test and the trust-layer-ordering test
    (§4.5) — so the four memories collapsed to one and the property under test could
    no longer be observed. Both now pass `dedupeExact: false` and say why. The
    defaults were **not** weakened to accommodate them: the tests were about
    reranking and trust, and deduplication is orthogonal to both.
  - **A real release-gate defect found on the way.** `npm run release:check` failed
    with exit 134 — the known native SQLite teardown abort
    (`RemoveEnvironmentCleanupHook` in `Statement::~Statement()`) inside
    `scripts/bench-tenant.sh`. `scripts/run-tests.mjs` has retried that for the test
    suite for some time, which is why the suite is reliable while the tenant
    benchmark was not: it made the release gate fail nondeterministically on a
    measurement that had already completed. The script now applies the same bounded
    retry. Verified that a *real* failure still fails — removing the sample script
    makes the benchmark exit non-zero after exhausting its attempts, so the retry is
    not masking anything.
  - Which copy survives is real behaviour I would have shipped unstated: the
    pipeline **sorts before deduplicating**, so the survivor is the best-*ranked*
    copy, and where scores tie exactly the lowest id wins. It is not input order.
    T04-013b pins both halves separately after I first conflated them.
  - Verified by mutation: dedup unwired from the pipeline → 9 failures; exact off by
    default → 9; same-source on by default → 5; detection bypassed to raw
    lowercase-trim → 3; provenance keyed on `sourceType` alone → 5.
  - 2 of my own premises were wrong. I assumed the first corpus entry survived
    deduplication when the pipeline's sort decides otherwise, and I conflated
    `dedupeResults`' first-input-wins rule with `searchQ`'s id tie-break into one
    assertion that could not hold.
  - Acceptance: exact duplicates are detected by normalized content, not by
    embedding similarity, so they are caught with embeddings off. Same-source
    duplicates are grouped by provenance source. Both suppress results and delete
    nothing.
  - Verification: identical text is collapsed in the **default**
    (`embeddingProvider: none`) configuration, which is where the audit found it
    silently passing through. Duplicate rate from T01 drops.
  - Depends on: T01.
  - Scope: M.
- [x] **T05 — Superseded-memory suppression.**
  - Outcome: superseded memories are excluded from results unless
    `includeSuperseded` is passed, exposed on HTTP search and the MCP `search` tool
    alongside the T04 escape hatches. 12 tests. Implemented in `searchQ` after the
    sort and before deduplication.
  - **Suppression only happens when the replacement is actually available.** A
    dangling `supersededBy` — deleted, archived, or scoped out of the pool — keeps
    the old copy visible, because replacing a stale answer with *no* answer is the
    wrong direction to fail in. This needed the most care and is pinned from both
    sides (T05-006, T05-007), plus an invariant that no query can come back empty
    (T05-011).
  - **A real bug in my first implementation, caught by T05-005.** I tried to make
    suppression "chain-aware" by suppressing a copy only when its superseder was *not
    itself* superseded. That is backwards: for `v1 → v2 → v3` it returned both v1
    and v3, because v1's superseder v2 *is* superseded. Chains need no handling at
    all — each link is suppressed because its successor is present — so the rule is
    one line and the comment records why the clever version was wrong.
  - `sanitizeMemory` already strips `supersededBy` when the target is not visible,
    and `assertTenantReferences` validates the target at write time, so a dangling
    reference is unlikely but not impossible. That is why the availability check is
    explicit rather than assumed.
  - Verified by mutation: suppression unwired → 13 failures; the old chain rule → 13;
    a dangling reference suppressing anyway → 7; the flag inverted → 17.
  - 2 of my premises were wrong, both the same mistake: asserting against hardcoded
    ids like `"solo"` and `"unrelated"` for memories built without an `id` override,
    so the generated `m00X` id never matched.
  - Acceptance: a memory with `supersededBy` set is excluded from default results
    and retrievable via an explicit flag. Retrieval never deletes it.
  - Verification: the audit's `supersededBy` reproduction now returns only the
    superseding memory by default, and both when the flag is set.
  - Depends on: T04.
  - Scope: S.
  - Closed: default suppression confirmed and reasoned in "Decisions taken while
    implementing" §1 (audit open question 1).

### Phase 3: Budget and weights

- [x] **T06 — One context budget object.**
  - Outcome: `RetrievalBudget` and `BudgetReport` in `src/types.ts`, applied in
    `searchQ` and reported on the result. `maxBytes` and `maxLatencyMs` did not
    exist anywhere in the tree before this; `maxTokens` and `maxItems` existed as
    unrelated parameters, which is exactly the problem — expressing "8k tokens and
    16KB and 200ms" needed three unrelated arguments. 15 tests.
  - **Exceeding `maxLatencyMs` returns the best results so far and says so**, per the
    plan's decision. The bound exists so retrieval degrades under load; degrading
    into *no* answer is the opposite, and silent truncation would be its own lie, so
    `truncated_by` names the bound responsible.
  - **A budget never starves a query.** The first result is always admitted, so
    `maxBytes: 1` yields one result rather than none. A bound that returns nothing
    has not degraded, it has failed.
  - **Three defects in my first implementation, all found by the tests:**
    1. The pre-existing `slice(0, effectiveLimit)` ran *before* the budget, so with
       `maxItems: 3` the budget had nothing left to remove and the report claimed
       `truncated: false` on a result set that had been truncated. The budget now
       has to be the thing that truncates, or its report cannot tell a caller
       anything.
    2. `maxItems: 0` returned nothing while reporting a complete result. A malformed
       budget is now rejected with `INVALID_INPUT`, matching `selectContextMemories`.
    3. With only a latency budget set, the **default** limit truncated the list and
       the report blamed "maxItems" — a bound the caller never set. The report now
       names only the caller's own bounds.
  - `maxBytes` counts **UTF-8 bytes**, so a CJK result is measured at three times
    its character count. Verified by mutation: counting characters instead fails
    T06-006.
  - Verified by mutation: budget never applied → 23 failures; latency throws instead
    of degrading → 7; truncation never reported → 7; the budget can return nothing
    → 5; the default limit blamed on the budget → 3; bytes counted as characters
    → 1.
  - **Two of my tests guarded nothing**, found by mutation: the multi-byte test
    used assertions that happened to hold under *both* byte and character counting
    (both totals are "under 40"), and the "don't blame an unset bound" test used a
    latency budget that fired *before* the default limit was ever reached, so the
    case it guarded never ran. Both rewritten to assert the distinction directly.
    Worth noting that all 15 tests passed on the first run — a first-run pass is
    not evidence, which is exactly why the mutation step exists.
  - The compiler turned out to be the better guard for one mutation: making the
    budget un-appliable broke type narrowing and would not compile.
  - Acceptance: `maxTokens`, `maxItems`, `maxBytes`, and `maxLatency` are fields
    of one budget. Exceeding the latency budget returns the best results so far
    with a flag saying so, rather than an error.
  - Verification: a budget with all four bounds is honoured simultaneously; each
    bound alone is tested; a slow provider degrades to partial results instead of
    failing.
  - Depends on: T04.
  - Scope: M.
  - Closed: degrade-rather-than-fail confirmed and reasoned in "Decisions taken while
    implementing" §2 (audit open question 3).
- [x] **T07 — Configurable fusion weights.**
  - Outcome: `FusionWeights` in `src/retrieval.ts` with `DEFAULT_FUSION_WEIGHTS`
    frozen, threaded through `rrfFuse`, `modifierScore`, the single-list fusion
    helper, and both `searchQ` call sites in `src/service.ts`. Configurable from
    the policy file (`retrieval.fusionWeights`) and from
    `REMEMBRA_RETRIEVAL_FUSION_WEIGHTS=name=value,...`; unknown names are
    rejected rather than ignored, so a typo cannot leave a deployment on
    defaults it did not ask for.
  - Three things were wrong on the first attempt, and all three produced a
    *passing* test that proved nothing:
    - An edit to the RRF denominator silently failed to land, so the weights
      reached the ordering but never the score. The first probe looked fine
      because the ranking was unchanged anyway. A `python3` `str.replace`
      without an assertion is not an edit.
    - I asserted that `rrfK` and `fusionScale` reorder results. They cannot.
      `rrfK` is monotone in rank and `fusionScale` is a common multiplier, so
      on a corpus where the signals agree neither can change the order. T07-008
      and T07-009 now assert what they actually control — score compression and
      the balance against the modifiers — and a third test proves the defaults
      are not beaten by either reweighting.
    - Test corpora that varied one attribute and held the text identical were
      silently returning a *single* result, because T04's default-on
      deduplication collapses identical text. Three had to be given distinct
      content. That is the second time T04 has done this.
  - A fourth finding came out of mutation testing: `rrfK` was untested in the
    two-list path, because every `rrfK` corpus was a single-list query, so
    routing `rrfFuse` back to the hardcoded constant changed nothing observable.
    `rrfFuse` is exported, so T07-015 pins its formula directly.
  - Two more survivors were fixed rather than tolerated. The policy deep-merge
    for nested weights turned out to be **dead code** — `defaults.retrieval`
    never carries the key — and was deleted. And a non-finite weight was
    reachable from a policy file, because YAML spells both `.inf` and `.nan` and
    `z.number()` accepts them; `weightSchema` now requires finite and
    non-negative, and T07-025 covers it.
  - The zod form is deliberate and non-obvious: in zod 3.25 a
    `.strict().partial()` object used as a *nested* key comes back **required**,
    so the optionality does not survive nesting and an unconfigured deployment
    failed to load. `.optional()` on the key and on each field is the form that
    works. Noted in the schema so it is not "simplified" back.
  - The relation-expansion re-rank is a second `searchQ` over the expanded pool.
    It was spelled out separately from the first call, so a weight could apply to
    one and not the other. Both now share one `searchPolicy` object, and T07-026
    exercises the second call to prove it.
  - The benchmark-set acceptance needed two discarded fixtures first: one was
    saturated at MRR 1.0, and the next was three keyword-gold queries to one
    semantic-gold, so "lexical-heavy" merely reproduced the default score. The
    fixture that works is balanced two-and-two, with each query's gold answer
    matching on one signal and its decoy on the other.

### Phase 4: Guardrail

- [x] **T08 — Enforce the benchmark gate.**
  - Acceptance: every retrieval change runs the benchmark set, and the gate fails
    on a regression in precision, recall, MRR, nDCG, duplicate rate, or latency
    percentile. §38's rule becomes mechanical rather than aspirational.
  - Verification: a deliberately degraded ranking fails the gate.
  - Depends on: T01, T02, T04.
  - Scope: M.

  - Outcome: `src/benchmark-set.ts` holds a labelled corpus of 32 documents and 23
    scenarios, each naming the regression it guards, run through the real
    `searchQ` pipeline and scored by `src/eval.ts`. `benchmark/baseline.json` is
    the committed baseline. `compareToBaseline` is the single comparison
    implementation, used by both `src/test/benchmark-gate.test.ts` (in the suite)
    and `scripts/benchmark-gate.mjs` (the release stage), so the two can never
    disagree about what counts as a regression. `bench:gate` is wired into
    `release:check` ahead of the security matrix.
  - Latency is gated only in the standalone script. The suite runs files in
    parallel, so a p95 wall-clock assertion there would measure scheduling rather
    than retrieval, and a gate that fires for reasons outside the change under
    review is a gate people re-run until it goes green. The quality metrics are
    deterministic (fixed clock, no provider, no network) and are asserted in both
    places.
  - Four things had to be true before the set measured anything, and none of them
    were true at first:
    - **It has to run the real pipeline.** The pre-existing `benchmark.test.ts`
      passes a hand-written substring `searchFn`, so it measures the harness and
      not the engine. A gate over it cannot see a broken ranker.
    - **A scenario needs headroom.** Every scenario with an unambiguous winner can
      only detect a catastrophic regression. Three hard cases were added where a
      plausible wrong answer leads, so a ranking that drifts by a place or two is
      visible.
    - **The synthetic vector must not be the keyword signal.** Whole-word hashing
      was tried first and made paraphrase untestable — a query sharing no
      vocabulary with its answer had similarity exactly zero, so "semantic" was
      just lexical with different arithmetic. Character-trigram hashing gives a
      crude but real fuzzy match, and the two signals then genuinely disagree.
    - **The result window has to be smaller than the corpus.** At `k` = corpus size
      every document is returned, so `precision@k` is a constant and carries no
      signal at all. It is 5.
  - The most instructive failure was a metadata-heavy document that topped 12 of 13
    queries. Its ~110-point modifier bonus beat any fusion score, so the benchmark
    was measuring pinning. The fix was to make the corpus uniform in metadata so
    fusion is the only variable — and the lesson generalised into a property: a
    bonus larger than the entire spread between two fused scores cannot be tested
    in a shared corpus, because it wins everything. That is why scenarios can carry
    a **private corpus** that replaces the shared one. Two attempts failed first
    (one made a corpus where a single memory topped all 19 scenarios; the next made
    the private corpus *additive*, and a high-metadata document from the shared
    corpus still outranked the private pair).
  - Mutation testing found every remaining hole, and most of them were scenarios
    that named a behaviour they did not test:
    - Inverting trust in a pair that also differed in importance and provenance
      changed nothing. Each modifier now has a pair differing in exactly one
      field, in a private corpus.
    - Confidence was invisible because every document carried the default 1, so
      the term never varied. A term that does not vary is invisible to a gate no
      matter how well the gate is written.
    - Recency was invisible for the same reason, and then still was after a pair
      was added: every document shared one `updatedAt`. Worse, recency cannot
      overcome a rank difference in the default path at all — one rank is worth
      ~27 points and the contribution is capped at 20 x 0.5 = 10 — so it can only
      break a tie. The pair now carries identical embeddings to force that tie.
    - Dropping the recency term entirely is *undetectable*, and for a reassuring
      reason: the tie-break is `final`, then `updatedAt` descending, then id, so
      two tied documents are still ordered newest-first. The code is more robust
      than the gate can measure. The scenario says so instead of claiming
      otherwise.
    - A mis-scaled recency term is likewise undetectable: recency is monotone in
      age and the scale is a positive multiplier on both sides, so no scale
      reorders a pair that is already ordered correctly. Stated in the guards.
    - The phrase bonus was masked by the vector path ranking the ordered document
      first for unrelated reasons, and then by a third document ranked between the
      pair. The pair is now private and carries no embeddings.
    - The CJK branch of `tokenize` is unreachable — `extractQuery` filters query
      terms with `/^[a-z0-9]+$/u`, so every non-ASCII query yields zero terms and
      no lexical match. Recorded as audit finding S7 and deliberately **not** gated:
      a stage that fails on correct code is not a gate. The fix is one line but it
      is a behaviour change on a public surface and wants its own decision.
  - A defect in this work's own tooling, worth recording: `BENCH-GATE-001` checks
    that every scenario's `relevantIds` exist, and it caught a whole block of
    documents I had deleted by accident while moving the private pairs. It also
    caught the stale baseline. Both would otherwise have shipped as a benchmark
    quietly measuring less than it claimed.
  - Also found, pre-existing and not part of this task: `totalScore` in an
    `explain` result is the sum of *all* components, including the raw `keyword`
    and `semantic` sub-scores, but the ranking is sorted by `final`
    (`fusion x scale + modifiers + scope`). So the reported score is not the score
    the order is determined by, and two documents can be reported out of order
    relative to their own totals. It cost real time while tuning scenarios — the
    benchmark is built on it — so it is worth a decision rather than a footnote.

## Found while releasing 5.7.1

- **Two cold-start races in the batch idempotency ledger**, found by building a
  reproduction instead of re-running a suite. The symptom was one MATRIX-02 failure
  that passed on every rerun. The reproduction cold-starts a store from 16 concurrent
  processes against a fresh claim directory, 60 rounds. Against the unmodified store it
  fails routinely — hundreds of times — almost entirely on the integrity-key staging
  window; with the fixes, zero. Two rarer symptoms in the same family survive and are
  recorded rather than patched: this store has now produced six manifestations, and the
  5.6.0 note already prescribes a single atomic initialisation instead of another
  patch.
  - Both shipped fixes are now mutation-verified. The `claims.identity` `link()` fix
    had **no test at all** and passed green on its first run, which is not evidence.
    Two tests now cover it, each caught by its own mutation: one spies `fs.openSync`
    and fails if the final path is ever created with `O_CREAT`; the other plants an
    identity staging file and is caught by narrowing `stagingEntry` back to
    `.claims.key` alone.
  - **The second test exists because the mutation survived everything else.** That
    narrowing was invisible to the unit suite *and* to 15 rounds of 16 concurrent cold
    starts, because a single process never sees its own identity staging file at scan
    time — the scan runs before the ledger identity is published. The defect is only
    reachable when a peer is already inside its publication window. A surviving
    mutation here is a statement about reachability, not about test quality, and it
    had to be settled with a targeted probe rather than left as a verdict.

## Found by publishing 5.7.0

Recorded here rather than in a task list, because these were found by installing the
release from the registry and using it — not by anything in the suite — and 5.7.0's
tag was already cut, so they are follow-up work rather than part of the milestone.

- **§37's budget was unreachable through the SDK.** `SearchInput`, which
  `SearchOptions` is an alias of, never gained `budget`. Adding it exposed a second
  half: the SDK serialises query parameters with `String(value)`, so a nested object
  became the literal string `"[object Object]"` and the server ignored it. Fixed by
  flattening nested parameters as `parent.child`. The response side had the same gap:
  the server returned `budget` all along and `SearchResponse` did not declare it.
- **`§37's budget was unreachable through `MemoryService` too**, and the report was
  discarded. That one was found before tagging, by asking how a caller would actually
  set the bound rather than by a failing test.
- **`extractQuery` dropped every non-ASCII query** (audit S7). Fixed on main: both
  halves of retrieval now share one tokeniser. The audit's own claim that katakana
  was uncovered was wrong — the range already includes `\u3040-\u30ff` — and the
  defect was wider, covering Hangul, Thai, Greek and Cyrillic too. Corrected in place.
- **`latest N <query>` silently searched for the literal words** (audit S8, new).
  Found while writing the S7 tests. `TEMPORAL_RE` anchored its alternation with `$`,
  so the qualifier only parsed when it was the whole query. Fixed on main: both
  branches carry a trailing remainder, with the digit count still required so
  "latest news ..." stays an ordinary query.
- **The temporal qualifier parses but does almost nothing** (also audit S8).
  `latestCount` and `recentCount` never limit to N, and `beforeMs`/`afterMs` are never
  read at all; the only effect anywhere is `modifierScore` switching the recency
  multiplier from 0.5 to 2. Measured and recorded. Unfixed: making them count and
  filter is new behaviour, not a fix, and needs a decision about ties, archiving and
  `validUntil`. The benchmark set has no temporal query, so the gate cannot see this
  path — the unit tests are what cover it.
- **The comparison between `SearchInput` and `SearchQuery` is now a compile-time
  assertion**, because no test compared them. It took three attempts: the first only
  named a type alias, the second reported on `type` and `scope` rather than on what
  was being checked (`Record` requires keys where the shape makes them optional), and
  the third built its source from the very keys it was checking, so removing `budget`
  produced no error at all. It is now "the missing set is empty", which cannot be
  satisfied by the thing it checks.

The pattern is worth naming, because it recurred: **a feature whose only tests stop at
the function under test cannot see a field a neighbouring layer forgets to forward,
and a hand-maintained type that shadows another one drifts silently.** Three of the
four defects above are that same shape.

## Decisions taken while implementing

The plan's open questions are settled here rather than left implicit in code. Each
is a reversible default, and the reasoning is recorded so a later change is a
decision rather than an accident.

### 1. Superseded memories are suppressed by default (T05)

**Decision: suppress, with an explicit `includeSuperseded` escape hatch.**

§36 forbids *destroying* historical records, which is a statement about storage and
not about retrieval, so it does not answer this. The question is what a query should
return when v1 has been superseded by v2, and the answer depends on which question
is being asked:

- *"What is the support policy?"* — the common case. Returning v1 and v2 side by
  side is wrong, and the audit reproduced exactly that: a candidate with
  `supersededBy` set survived alongside the memory that supersedes it.
- *"What did the policy say in January?"* — the uncommon case, and a real one. It
  needs v1.

Defaulting to suppression answers the common question correctly and leaves the rare
one available on request. Defaulting the other way would return a stale policy as
the top hit for every query that happens to match it and bury the current one — the
failure mode the audit found. Suppression removes a result from a result *set*;
nothing is deleted, and the memory stays readable by id and retrievable behind the
flag.

### 2. Exceeding `maxLatency` returns the best results so far, never an error (T06)

**Decision: return partial results, and report the truncation in the result.**

An error is the wrong answer for a memory system. `maxLatency` exists so retrieval
degrades under load, and degrading into *no answer* is the opposite of degrading:
every dependent call fails at exactly the moment the system is already struggling,
and the caller has nothing to work with.

Silent truncation would be its own lie — the caller cannot distinguish a complete
answer from a partial one, and would act on a fragment believing it whole. So the
budget is reported on the result rather than only logged, and a caller that needs
completeness can check while a caller that needs an answer gets one.

### 3. §32's "metadata filters" — deliberately not claimed

Filters inside the lexical scorer, or the existing `scope`/`type` filters promoted
into a declared filter object? The roadmap lists it under lexical retrieval, which
points at the former, but the existing filter surface already covers most of the
latter and this milestone is additive. Promoting those filters into a declared
object is a public-contract change that belongs to the tenancy slot (5.8.0), where a
filter object is actually needed.

**T02 delivered the two fields that exist** (`content` and `tags`); no new filter
surface is added, and the roadmap item is recorded as not claimed rather than
quietly skipped.

## Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Lexical scoring changes reorder existing results for current users | High | Defaults reproduce today's behaviour; the benchmark gate measures the delta before it ships |
| Deduplication hides a memory the user wanted | Medium | Suppression is a result-set decision, not a deletion; superseded copies stay retrievable behind a flag |
| Real IDF needs corpus statistics the caller does not have | Medium | Computed from the candidate set, bounded, and falling back to the current behaviour when statistics are unavailable |
| A latency budget silently truncates results | Medium | Truncation is reported in the result, never silent |
| Two new metrics pass no matter what | High | T01's acceptance requires each metric to fail on a deliberately broken input |

## What this milestone will not claim

- **No change to a single-process deployment's behaviour** beyond retrieval
  quality. No new dependency, no new required configuration, no change to the
  HTTP contract except additive optional budget fields.
- **Not a full vector-index replacement.** The brute-force cosine path stays; this
  milestone makes ranking and selection correct, not asymptotically faster. That
  is §52–§58's slot.
