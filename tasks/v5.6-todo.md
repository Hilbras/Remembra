# V5.6.0 Task List: Distributed Remembra

Status: started from V5.5.1 (`c3334b8`) plus the S1 compare-and-swap fix. The
roadmap calls this milestone V5.2.0/V5.2.1 (§25–§30); it is numbered V5.6.0
because V5.4.0 shipped before V5.1 and the slots were renumbered — see the
banner in `REMEMBRA_V5_TO_V6_ROADMAP.md`.

Nothing in this milestone may add a required runtime dependency, and nothing may
change a single-process deployment's behaviour.

Source plan: [`v5.6-plan.md`](v5.6-plan.md)
Audit: [`v5.6.0-audit.md`](../docs/v5.6.0-audit.md)

## Phase 0: Audit

- [x] **V5.6-T01 — Audit the single-host assumptions**
  - Acceptance: every in-process and durable state that N instances would
    duplicate or contend for is recorded, with the `src/backend.ts` concurrency
    contract checked against each mutating path.
  - Verify: reproduction with two backend instances over one database.
  - Depends on: V5.5.1.
  - Progress: complete. `docs/v5.6.0-audit.md` records S1–S6. **S1 was a
    high-severity data-loss bug and is fixed**: `SqliteBackend.withLock` is a
    per-instance promise queue with no `BEGIN IMMEDIATE` and no
    `db.transaction()` anywhere, and `update` checked `expectedVersion` in
    application code before writing `WHERE id = ?` with no version predicate.
    Two instances reading the same version both wrote and both were told they
    succeeded — reproduced 5 times out of 5, one write silently discarded. The
    write is now a compare-and-swap, with `NOT_FOUND` distinguished from
    `CONFLICT` so a caller does not retry a write whose row is gone. Six tests in
    `src/test/sqlite-cas.test.ts`. S2–S6 are recorded and deliberately not
    changed blind: each needs its own decision about the right predicate or
    boundary.

## Phase 1: Cross-instance primitives, no Redis

- [x] **V5.6-T02 — Introduce a `LockProvider` interface with leases**
  - Acceptance: `acquire`, `renew`, `release` carrying owner, lease expiry, and
    reclamation of an aged-out lease; an in-process implementation that is what
    runs today, plus a file-backed one with a real cross-process story.
  - Verify: two providers contending; expiry reclaimed by a peer; renewal blocks
    reclamation; release by a non-owner refused.
  - Depends on: V5.6-T01.
  - Progress: complete. `src/lock.ts` adds `LockProvider`, `LockHandle`,
    `InProcessLockProvider`, `FileLockProvider`, `lockKey`, and `withLock`.
    Every acquisition is a **lease** with an owner and an absolute expiry rather
    than a lock, so a crashed holder is reclaimed instead of deadlocking — which
    is the failure mode a distributed lock invites. Two rules are enforced and
    pinned: `release()` is owner-checked and cannot clear a peer's lease, and
    `renew()` returns `false` once a lease is lost, so a partitioned worker stops
    working instead of resuming on a belief it still holds it. `lockKey` hashes
    any non-digest part, so a raw tenant cannot reach a key that is written to
    disk. `FileLockProvider` reclaims on the expiry timestamp rather than
    pid liveness, which is what makes it portable; the pid stays only as a fast
    path. Audit S6's one-host question is answered; the cross-host boundary is
    stated for T05. 15 tests, and **two of them caught defects in this
    implementation**: an unreadable lease file made `acquire` livelock forever
    (it could not tell "unparseable" from "vanished", so it retried the create
    without ever removing the blocker), and `isHeld()` returned false for a lease
    it had just written because the acquired file was never recorded. A third
    finding was mine rather than the code's: the in-process tests initially used
    two provider instances, which cannot contend by construction — an in-process
    provider is per-instance, and testing it that way would have asserted
    nothing. `LOCK-006b` records why a bounded wait needs a real clock.

- [x] **V5.6-T03 — Add a durable job ledger with the §27 job model**
  - Acceptance: the six states and the ten required fields; atomic claims so
    exactly one worker can hold a job; a `JobStore` interface with in-memory and
    SQLite implementations.
  - Verify: two claimers, one winner; expiry makes a job claimable again; a
    completed job is never re-claimed; payload and tenant are bounded.
  - Depends on: V5.6-T02.
  - Progress: complete. `src/job-store.ts` adds `JobStore` with
    `InMemoryJobStore` and `SqliteJobStore`, published as
    `@hilbras/remembra/job-store`. The existing promise-based `JobQueue` is
    unchanged and stays what a single process uses — a promise created in one
    process cannot be resolved from another, so the shared path is polled rather
    than awaited, and pretending otherwise would be the wrong shape. All six §27
    states and all ten fields are carried. **A claim is one statement**
    (`UPDATE ... RETURNING`), so the database chooses the winner and hands back
    the row it actually claimed; a read-then-write would be the S1 shape again.
    Claims are ordered oldest-first with the id as tie-break, so every claimer
    agrees on the next job — order within a millisecond is arbitrary, but it is
    the *same* arbitrary order for everyone, which is what stops two workers
    racing for one job. A dead worker's job returns to `retrying` on lease
    expiry; `renew`, `complete`, and `fail` all return `false` for a lease that is
    no longer the caller's, so a partitioned worker cannot commit anything.
    Bounded throughout: 64 KiB payloads, a safe-shape `type` (it becomes a metric
    label), hashed tenant digests, and a classified error code rather than a
    message. 28 tests — the whole behavioural suite runs against **both**
    implementations so they cannot drift, plus two cross-connection tests for the
    case the in-memory store cannot express.
  - Also found here: a **pre-existing** flaky failure in `foundation.test.ts`
    ("delete racing search never throws"), which disproved the audit's own S2
    assessment of `forget`. Two `MemoryStore` instances deleting the same memory
    could have one unlink the file after the other resolved it, and the `ENOENT`
    surfaced as an `IO_ERROR` to a caller that had done nothing wrong. `ENOENT` on
    the unlink is now the already-reported "missing" result, so a racing delete is
    genuinely idempotent. The audit row is corrected: idempotent *state* is not the
    same as a non-throwing *call*, and only the second keeps a caller from having
    to distinguish "someone else did it" from "something broke".

- [x] **V5.6-T04 — Run the existing job queue on the durable ledger**
  - Acceptance: `JobQueue` takes a `JobStore`; single-host default is the
    in-memory store, so nothing changes for one process; durable mode survives a
    worker restart and never runs a job twice concurrently.
  - Verify: restart mid-job reclaimed after expiry; duplicate delivery is a no-op.
  - Depends on: V5.6-T03.
  - Progress: complete, with the plan's wording corrected first. It said "`JobQueue`
    takes a `JobStore`", which contradicts what T03 established: a promise
    created in one process cannot be resolved from another, so a shared queue is
    polled rather than awaited. `JobQueue` is therefore untouched and remains
    what a single process uses; `src/durable-worker.ts` adds `DurableWorker`,
    published as `@hilbras/remembra/worker`.
    The **partition guard** is the centrepiece: a claimed job's lease is renewed
    while it runs, and if a renewal ever fails the job's `AbortSignal` fires.
    Finishing anyway would be the S1 lost-update failure wearing a lease — two
    workers each believing they own one job. A `complete()` that returns `false`
    is likewise reported as `lease_lost`, not as success. Claims are restricted to
    the types a worker declares, so it never claims work it cannot run, which is
    how §28's heterogeneous split falls out without a second mechanism; starting
    a worker with no handlers is refused rather than left polling pointlessly.
    `stop()` *releases* in-flight leases rather than abandoning them, so a peer
    takes the work immediately instead of waiting out the lease. 11 tests.
  - A deliberate design point: the worker's poll timer is **not** `unref`'d,
    because §28 allows a worker-only process and nothing else would hold its
    event loop open — an unref'd timer would let it exit before claiming a
    single job. `stop()` is therefore required, and the tests that start a worker
    all stop it. That trade-off immediately caught one test leaking a worker and
    hanging the file, which is the intended lesson rather than an accident.

## Phase 2: Shared state (optional)

- [x] **V5.6-T05 — Add the Redis adapter behind the existing interfaces**
  - Acceptance: a shared `RateLimiter` and `LockProvider` over an optional peer
    reached only by dynamic `import()`. `redis` is never a `dependencies` entry.
  - Verify: absent `REMEMBRA_REDIS_URL` imports nothing; URL set without the
    package fails startup with a named error; two processes share one budget.
  - Depends on: V5.6-T04.

  - Progress: complete. `src/redis.ts` adds `RedisLockProvider` and
    `RedisQuotaRateLimiter`, published as `@hilbras/remembra/redis`.
    **`redis` is an optional peer and deliberately not even a devDependency** —
    keeping it uninstalled is what makes the missing-package startup failure a
    real test instead of a mocked one, and REDIS-006 asserts the manifest so a
    later convenience cannot quietly turn that into theatre.
    There is **no fallback anywhere**: unset means single-host and imports no
    Redis code at all; set-but-absent and set-but-unreachable both fail startup
    with a named remedy. A deployment that asked for a shared budget and quietly
    got a per-instance one would report a limit it is not enforcing while looking
    healthy, so that is a failure to start rather than a degraded mode.
  - The quota is **one Lua script covering every dimension**, not N limiters
    composed under the existing `QuotaRateLimiter`. That was my plan's wording and
    it is wrong for a shared store: `QuotaRateLimiter` serializes dimensions with
    an *in-process* mutex, so N instances would interleave their dimension checks
    and a shared organization budget could be exceeded by concurrent requests.
    That is check-then-act — audit finding S1, one level up. One script charges
    only if every dimension allows, and a refusal charges nothing anywhere.
  - **Three defects found and fixed while writing it**, each of which would have
    been invisible in review:
    1. Precedence taken from the config object's key order, so which budget
       reported a refusal depended on how the operator wrote their config. Now
       `RATE_LIMIT_DIMENSIONS` with base last, identical to `QuotaRateLimiter`.
    2. **One window shared by every dimension.** Pruning each key against the
       largest window present left a short window's stale entries in place, so
       `ZCARD` counted hours-old requests and a 60-per-minute budget enforced
       over an hour. A limit that reads as configured and enforces over the wrong
       period is worse than no limit.
    3. `tightestRemaining` seeded to `-1` and only ever assigned under `<`, so the
       first iteration never matched and every allowed reply reported the wrong
       remaining count.
    Also: an absent dimension was being charged against a key it should not have
    touched, which multiplies one request's charge by the number of configured
    dimensions it happens to be missing; and policies were unvalidated, so an
    invalid limit would have shipped into a Lua script. `assertPolicy` is now
    exported from `quota.ts` and both limiters use the same function.
  - **On verifying the Lua without a Redis server.** A fake client cannot check a
    script's logic, so the alternative was shipping the atomicity argument
    unexecuted. I installed `fengari` (a Lua 5.3 VM in JS) *outside* the repo and
    ran the **actual script text extracted from `src/redis.ts`** against a shim
    of the Redis commands used — 28 checks covering per-dimension windows,
    precedence, tightest reporting, the same-millisecond `ZADD`-overwrite hazard,
    non-consuming `check`, window boundaries matched against
    `InProcessRateLimiter`, and owner-checked renew/release. The harness is
    committed as `scripts/verify-redis-lua.mjs` (extracting from source, so it
    cannot pass against a stale copy) and **is not a release gate**: a Lua VM is
    not a runtime requirement, and adding one to turn a check green would trade a
    real constraint for comfort. Without fengari it refuses with exit 2 and
    instructions.
  - I checked the tests have teeth rather than assuming it: reintroducing the
    precedence bug fails REDIS-010 and REDIS-012, the absent-dimension bug fails
    REDIS-011, and reintroducing either Lua bug fails 7 and 5 of the 28 Lua checks
    respectively. Two mutants came back *equivalent* — the order is derived from
    `RATE_LIMIT_DIMENSIONS` in two independent places, so a partial revert is
    genuinely harmless rather than merely untested.
  - **Still unverified: a live Redis server.** Every adapter test uses a fake
    client with canned replies. Before production use, run against a real server
    and confirm the scripts load under the deployed Redis version. Stated in
    `docs/lock.md` rather than left for someone to discover.
  - 18 wiring tests. Of my own test premises, six were wrong and corrected rather
    than worked around: dimension values must be opaque digests (the identity
    helper correctly refused `u1`), `user` precedes `apikey` in the declared order
    (so my "reversed" object was not actually reversed, and the first version of
    that test could not have caught the bug), the script's reply index is 1-based,
    and I miscounted the argument list as 9 entries when it is 8.
