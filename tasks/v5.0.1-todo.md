yet.

Source plan: [`v5.0.1-plan.md`](v5.0.1-plan.md)

## Phase 0: Baseline and reproductions

- [ ] **V5.0.1-T01 — Establish the hotfix audit baseline**
  - Acceptance: confirmed findings, scope/non-goals, regression IDs, and current build/test baseline recorded.
  - Verify: `npm run build`, `npm test`, focused security/recovery tests, audit review.
  - Depends on: none.

## Phase 1: Authentication and rate limiting

- [ ] **V5.0.1-T02 — Authenticate before consuming protected rate limits**
  - Acceptance: anonymous/invalid requests cannot consume the valid protected bucket; trusted resolution remains after authentication.
  - Verify: `SEC-RL-001` reproduction (401 then success, not 401 then 429), invalid-key sequence, protected route matrix, full suite.
  - Depends on: V5.0.1-T01.

- [ ] **V5.0.1-T03 — Separate safe anonymous and authenticated rate identities**
  - Acceptance: no raw API key in limiter state; anonymous and authenticated buckets are distinct and documented.
  - Verify: `SEC-RL-002`, client/tenant isolation, limiter key/log inspection.
  - Depends on: V5.0.1-T02.

### Checkpoint: Authentication/rate limiting

- [ ] `SEC-RL-001` and `SEC-RL-002` pass.
- [ ] Invalid credentials cannot block a legitimate protected client.
- [ ] No raw secret appears in limiter state, logs, or test output.

## Phase 2: Central log redaction

- [ ] **V5.0.1-T04 — Add centralized structured-log redaction**
  - Acceptance: sensitive fields, nested values, headers, bearer tokens, and secret-bearing messages redact consistently in JSON/text.
  - Verify: `SEC-LOG-001`, `SEC-LOG-002`, bounded recursion, existing log tests.
  - Depends on: V5.0.1-T01.

- [ ] **V5.0.1-T05 — Remove secret-bearing debug and provider error fields**
  - Acceptance: debug/provider logs contain bounded sanitized diagnostics, not raw queries, bodies, URLs, credentials, or stack traces.
  - Verify: `SEC-LOG-003`–`SEC-LOG-005`, provider fault-injection tests, JSON/text capture.
  - Depends on: V5.0.1-T04.

### Checkpoint: Secret-safe telemetry

- [ ] Central and call-site redaction tests pass.
- [ ] Provider/public error sanitization tests pass.
- [ ] Security review approves telemetry changes.

## Phase 3: Storage startup integrity

- [ ] **V5.0.1-T06 — Make SQLite initialization fail closed by default**
  - Acceptance: SQLite/schema failure stops startup; explicit fallback requires opt-in, warning, and health visibility.
  - Verify: `SEC-STORAGE-001`, corrupt/future schema/missing root/FTS5/explicit fallback startup tests.
  - Depends on: V5.0.1-T01.

- [ ] **V5.0.1-T07 — Make startup migration readiness explicit**
  - Acceptance: automatic migration completes or fails before HTTP/MCP exposure; FTS degradation never switches backend.
  - Verify: legacy startup completion/failure tests, explicit migrate compatibility.
  - Depends on: V5.0.1-T06.

### Checkpoint: Storage integrity

- [ ] SQLite failure never silently changes data planes.
- [ ] Health identifies backend/fallback state.
- [ ] Startup migration readiness is deterministic.

## Phase 4: History path containment

- [ ] **V5.0.1-T08 — Validate memory IDs and contain history paths**
  - Acceptance: IDs/paths are validated and contained; symlinked history/sidecars rejected; missing history remains distinct from unsafe history.
  - Verify: `SEC-PATH-001`, direct backend/HTTP traversal, symlink read/write, tenant escape fixtures.
  - Depends on: V5.0.1-T01.

### Checkpoint: Filesystem security

- [ ] `SEC-PATH-001` passes for reads and writes.
- [ ] Tenant A cannot access tenant B/global history.
- [ ] Symlink/traversal failures are typed and observable.

## Phase 5: Strict snapshot tenant assignment

- [ ] **V5.0.1-T09 — Reject tenantless snapshots in ordinary strict restore**
  - Acceptance: signed tenantless/mixed/mismatched snapshots reject before destination access; same-tenant restore remains valid.
  - Verify: `SEC-SNAPSHOT-001`, file/SQLite preview/import, no-write, legacy compatibility.
  - Depends on: V5.0.1-T01.

- [ ] **V5.0.1-T10 — Separate explicit migration from ordinary import**
  - Acceptance: migration requires trusted target/mode/manifest, dry-run, verification, and honest report; ordinary import cannot enable it.
  - Verify: CLI subprocess, missing/wrong target/manifest, valid migration, partial failure/resume.
  - Depends on: V5.0.1-T06, V5.0.1-T09.

### Checkpoint: Tenant recovery correctness

- [ ] Strict restore never assigns tenantless data implicitly.
- [ ] Explicit migration is signed, target-bound, dry-runnable, verifiable, and recoverable.
- [ ] Tenant snapshot security review passes.

## Permanent regression IDs

- `SEC-RL-001`: authentication precedes protected rate consumption.
- `SEC-RL-002`: rate identities never contain raw secrets and are isolated.
- `SEC-LOG-001`: structured logs redact credentials and headers.
- `SEC-LOG-002`: central redaction covers nested/secret-bearing data.
- `SEC-LOG-003`: debug paths do not emit secret queries.
- `SEC-LOG-004`: provider errors do not leak secrets.
- `SEC-LOG-005`: auth failures do not log credentials.
- `SEC-STORAGE-001`: SQLite failure never silently changes backend.
- `SEC-PATH-001`: history paths reject traversal and symlinks.
- `SEC-SNAPSHOT-001`: strict restore rejects tenantless assignment.
- `SEC-TENANT-001`: all hotfix paths preserve tenant isolation.

## Stop conditions

- [ ] No security test is skipped, deleted, or weakened.
- [ ] No release occurs with a critical/high finding open.
- [ ] No raw secret appears in logs, limiter state, or test output.
- [ ] No strict restore silently assigns tenantless data.
- [ ] No history operation escapes its selected root.
- [ ] All release artifacts point to one commit.
