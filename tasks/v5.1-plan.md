# V5.1.0 Implementation Plan: Production Infrastructure

## Baseline

V5.0.3 is released at `324a6459bb7258a2b55d14844059664ab8805a0b`.
Its Node 18.20.8 and Node 24.21.0 gates passed with 466 full tests, 64
security tests, 48 recovery tests, 36 documentation files, and zero audit
findings. V5.1 must preserve that security and compatibility baseline.


## Architecture Decisions

- Keep the existing authenticated HTTP behavior and additive API compatibility.
- Depend on interfaces for rate limiting, quota accounting, health checks, and
  shutdown coordination; ship an in-process implementation first.
- Keep identity resolution opaque and derive quota dimensions only after
  authentication; never trust public tenant, user, agent, or API-key fields.
- Keep liveness cheap and public; readiness and dependency health expose bounded
  state and never expose memory content, secrets, or provider diagnostics.
- Make all counters/histograms low-cardinality and structured logs free of raw
  queries, credentials, and tenant payloads.
- Use bounded timeouts and deterministic drain semantics for shutdown.

## Task List

### Phase 0: Audit and contracts

- [ ] T01 — Audit current rate limiting, health, metrics, logging, and shutdown.
  - Acceptance: concrete compatibility gaps, cardinality risks, and dependency
    boundaries are recorded before implementation.
  - Verification: source audit, focused baseline tests, and failure matrix.
  - Scope: S.

### Phase 1: Rate and quota foundations

- [ ] T02 — Add a stable RateLimiter interface and in-process implementation.
  - Acceptance: `check`, `consume`, and `reset` are async, bounded, typed, and
    injectable without changing current authentication-before-limit behavior.
  - Verification: identity isolation, window expiry, reset, and HTTP parity.
  - Depends on: T01.
  - Scope: M.

- [ ] T03 — Define the multi-dimensional quota contract.
  - Acceptance: global, tenant, project, user, agent, key, IP, endpoint, and
    provider dimensions have typed policies, defaults, and deterministic
    precedence; missing dimensions cannot widen access.
  - Verification: quota matrix, bypass tests, and configuration validation.
  - Depends on: T02.
  - Scope: M.

### Phase 2: Health and observability

- [ ] T04 — Separate liveness, readiness, storage, and provider health APIs.
  - Acceptance: `/health` compatibility is preserved while additive
    `/health/live`, `/health/ready`, `/health/storage`, and `/health/provider`
    routes expose bounded status and correct authentication rules.
  - Verification: route, status, state, fallback, and secret-redaction tests.
  - Depends on: T01.
  - Scope: M.

- [ ] T05 — Complete production metrics and percentiles.
  - Acceptance: request, rate-limit, memory, provider, storage, snapshot, and
    recovery metrics use bounded labels and expose p50/p95/p99 where useful.
  - Verification: metric exposition, reset isolation, and cardinality tests.
  - Depends on: T01, T04.
  - Scope: M.

- [ ] T06 — Standardize structured request/operation logging.
  - Acceptance: supported events carry request/operation metadata through a
    centralized redactor; raw queries, secrets, and unbounded tenant values are
    excluded.
  - Verification: structured log schema and secret/tenant isolation tests.
  - Depends on: T01.
  - Scope: M.

### Phase 3: Lifecycle and hardening

- [ ] T07 — Implement bounded graceful shutdown.
  - Acceptance: stop accepting requests, drain active work with a timeout, stop
    jobs, flush observability, close providers/storage, and report typed
    shutdown failures without hanging.
  - Verification: in-flight request, timeout, repeated-signal, and resource
    cleanup tests.
  - Depends on: T04, T05, T06.
  - Scope: M.

- [ ] T08 — Add V5.1.1 production stress coverage.
  - Acceptance: concurrency, large payload/search, provider timeout storms,
    rate-limit storms, database contention, shutdown/restart under load, and
    resource-leak checks are bounded and reproducible.
  - Verification: dedicated stress matrix on Node 18.20.8 and 24.21.0.
  - Depends on: T02–T07.
  - Scope: L, split into focused test slices.

### Phase 4: Release

- [ ] T09 — Document and release V5.1.0.
  - Acceptance: operational docs, compatibility notes, release gates, tag,
    GitHub Release, npm publication, and clean registry install all agree.
  - Depends on: T08.
  - Scope: S/M.

## Checkpoints

- [ ] After T03: existing authentication, rate-limit, and security suites remain
  green; no public identity field can select a quota identity.
- [ ] After T06: health/metrics/logging contracts are documented and bounded.
- [ ] After T08: stress/resource evidence is recorded on both supported Node
  runtimes.
- [ ] No V5.2 distributed/runtime implementation starts before T09 passes.

## Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Abstraction changes auth order or identity semantics | Critical | Preserve current flow and run permanent SEC-RL/SEC-AUTH regressions |
| Metrics/logs create high-cardinality or secret leakage | High | Central bounded labels/redaction and adversarial tests |
| Health checks become expensive or expose internals | High | Cheap liveness, bounded dependency probes, public response allowlists |
| Shutdown hangs or drops active writes | High | Deadline, idempotent phases, drain tests, retained recovery state |
| Premature Redis/distributed coupling | High | Keep V5.1 interfaces implementation-neutral; defer Redis to V5.2 |

## Open Questions

- Which quota dimensions are enabled by default in the first V5.1 release?
  Default: preserve the current global/IP/API-key behavior and add tenant/user/
  agent dimensions only when trusted host context is present.
- Should provider health be queried synchronously on readiness? Default: use
  bounded cached/provider capability state and never require optional provider
  keys for local readiness.
