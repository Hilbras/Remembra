# V5.1.0 Implementation Plan: Production Infrastructure

## Baseline

V5.0.3 is released at `324a6459bb7258a2b55d14844059664ab8805a0b`.
Its Node 18.20.8 and Node 24.21.0 gates passed with 466 full tests, 64
security tests, 48 recovery tests, 36 documentation files, and zero audit
findings. V5.1 must preserve that security and compatibility baseline.


## Architecture Decisions

- Keep the existing authenticated HTTP behavior and additive API compatibility.
- Depend on interfaces for rate limiting, quota accounting, health checks, and
  shutdown coordination; ship an in-process implementation first.
- Keep identity resolution opaque and derive quota dimensions only after
  authentication; never trust public tenant, user, agent, or API-key fields.
- Keep liveness cheap and public; readiness and dependency health expose bounded
  state and never expose memory content, secrets, or provider diagnostics.
- Make all counters/histograms low-cardinality and structured logs free of raw
  queries, credentials, and tenant payloads.
- Use bounded timeouts and deterministic drain semantics for shutdown.

## Task List

### Phase 0: Audit and contracts

- [x] T01 — Audit current rate limiting, health, metrics, logging, and shutdown.
  - Acceptance: concrete compatibility gaps, cardinality risks, and dependency
    boundaries are recorded before implementation.
  - Verification: source audit, focused baseline tests, and failure matrix.
  - Scope: S.
  - Outcome: recorded in [`docs/v5.1.0-audit.md`](../docs/v5.1.0-audit.md) —
    7 rate-limit, 2 health, 3 metrics, 4 logging, and 5 shutdown findings, with
    the two highest verified by reproduction: the limiter's window map is
    unbounded and reachable pre-auth (50,000 abandoned keys retained forever),
    and the unauthenticated `/health` route is not cheap — it performs storage
    reads and durable recovery-state writes on every call. `/metrics` is
    rate limited despite the source comment claiming it exempt, so a scraper
    loses observability during a rate-limit storm. 22 existing `logEvent` sites,
    none carrying a request id.

### Phase 1: Rate and quota foundations

- [x] T02 — Add a stable RateLimiter interface and in-process implementation.
  - Acceptance: `check`, `consume`, and `reset` are async, bounded, typed, and
    injectable without changing current authentication-before-limit behavior.
  - Verification: identity isolation, window expiry, reset, and HTTP parity.
  - Depends on: T01.
  - Scope: M.
  - Outcome: `RateLimiter` is now an interface (`check`/`consume`/`reset`, all
    async) with `InProcessRateLimiter` as the shipped implementation, injected
    through `HttpOptions.rateLimiter`. `check` decides without charging, so
    asking whether budget remains cannot spend it. State is bounded by a
    `maxIdentities` ceiling with deterministic expiry sweep and LRU eviction —
    the 50,001-entry reproduction is now 10,000. `rateLimitIdentity` refuses any
    dimension value that is not a hex digest, so a raw principal or API key
    cannot become a quota identity. 22 new tests: 16 unit, 6 HTTP parity.

- [x] T03 — Define the multi-dimensional quota contract.
  - Acceptance: global, tenant, project, user, agent, key, IP, endpoint, and
    provider dimensions have typed policies, defaults, and deterministic
    precedence; missing dimensions cannot widen access.
  - Verification: quota matrix, bypass tests, and configuration validation.
  - Depends on: T02.
  - Scope: M.
  - Outcome: `src/quota.ts` adds `QuotaPolicy`/`QuotaPolicies`,
    `parseQuotaPolicies` (`REMEMBRA_QUOTAS`), and `QuotaRateLimiter`, which
  composes one bounded `InProcessRateLimiter` per dimension. All nine §19
  dimensions are configurable; precedence is the declared order
  (organization → project → user → agent → apikey → ip → endpoint → provider)
  with the base budget last, so a denial always names the same dimension for
  the same state. Charging is all-or-nothing, and a dimension is only charged
  when the request carries a trusted value for it — an absent dimension cannot
  widen access because the base budget still applies. 20 tests, including the
  full nine-dimension matrix and ten configuration-failure cases.

### Phase 2: Health and observability

- [x] T04 — Separate liveness, readiness, storage, and provider health APIs.
  - Acceptance: `/health` compatibility is preserved while additive
    `/health/live`, `/health/ready`, `/health/storage`, and `/health/provider`
    routes expose bounded status and correct authentication rules.
  - Verification: route, status, state, fallback, and secret-redaction tests.
  - Depends on: T01.
  - Scope: M.
  - Outcome: four additive routes. `/health/live` is public and reads process
    state only, so it stays 200 when storage is broken and reports `draining`
    once shutdown begins. `/health/ready`, `/health/storage`, and
    `/health/provider` sit after authentication, inheriting the existing rules.
    `/health` keeps its exact response and status codes, and its result is now
    cached for `REMEMBRA_HEALTH_CACHE_MS` (default 1s) with single-flight, so
    the unauthenticated route no longer drives a storage scan per request. All
    three dependency routes carry no content, no path, no error message, and no
    provider key. Documented in `docs/openapi.yaml` with new schemas. 15 tests.

- [x] T05 — Complete production metrics and percentiles.
  - Acceptance: request, rate-limit, memory, provider, storage, snapshot, and
    recovery metrics use bounded labels and expose p50/p95/p99 where useful.
  - Verification: metric exposition, reset isolation, and cardinality tests.
  - Depends on: T01, T04.
  - Scope: M.
  - Outcome: `MetricsRegistry` gained `quantile`, `summary`, `names`, and
    `seriesCount`, so p50/p95/p99 are readable from recorded histograms. The six
    §21 series that were missing are declared and now recorded, including
    `remembra_rate_limit_hits_total{dimension}` which the quota contract made
    possible. Audit finding M4 turned out to be the serious one: **seven further
    series were declared and never written by anything** — the four provider and
    storage series now have a real choke point in `observeProviderCall`, while
    the three memory-count gauges, three rate gauges, the cost gauge, and
    `remembra_token_usage_total` were removed because each needs a full scan or
    data the adapter contract does not report, and a declared series that can
    never report is a worse lie than an absent one. `JobType` labels are bounded
    to a closed set at both the enqueue and completion sites. 15 tests.

- [x] T06 — Standardize structured request/operation logging.
  - Acceptance: supported events carry request/operation metadata through a
    centralized redactor; raw queries, secrets, and unbounded tenant values are
    excluded.
  - Verification: structured log schema and secret/tenant isolation tests.
  - Depends on: T01.
  - Scope: M.
  - Outcome: `logEvent` now merges an `AsyncLocalStorage` request context, so all
    ~50 call sites get `requestId`, `operation`, hashed `tenantId`/`agentId`, and
    `durationMs` without threading anything by hand. A field policy enforces
    §22's exclusions structurally: content and path fields are dropped unless
    `REMEMBRA_DEBUG` is set, and identity fields are replaced by a short stable
    digest so correlation survives without a raw identifier reaching a log
    aggregator. Two pre-existing leaks were fixed: the retrieval debug trace
    logged the raw query behind `REMEMBRA_DEBUG_RETRIEVAL` rather than the
    documented `REMEMBRA_DEBUG`, and `migration_start` logged a storage path
    unconditionally. One `http.request` completion line per request. 16 tests.

### Phase 3: Lifecycle and hardening

- [x] T07 — Implement bounded graceful shutdown.
  - Acceptance: stop accepting requests, drain active work with a timeout, stop
    jobs, flush observability, close providers/storage, and report typed
    shutdown failures without hanging.
  - Verification: in-flight request, timeout, repeated-signal, and resource
    cleanup tests.
  - Depends on: T04, T05, T06.
  - Scope: M.
  - Outcome: `src/shutdown.ts` adds `ShutdownCoordinator` and
    `registerStandardShutdownPhases`, implementing §23's sequence in order. One
    deadline covers the whole shutdown; a wedged phase is reported `timeout` and
    the phases after it `skipped`, so storage is never closed under an in-flight
    write. A repeated signal joins the in-flight shutdown and shortens the
    deadline. The exit code is `1` for a forced shutdown, which the old
    always-`exit(0)` handler could not express. `startWebhookDrain` now returns a
    stop function, `closeProviders`/`backendForShutdown` were added to the
    service, and **MCP mode installs signal handlers at all** (audit S5). 15
    tests, all clock-driven — no wall-clock timers.

- [x] T08 — Add V5.1.1 production stress coverage.
  - Acceptance: concurrency, large payload/search, provider timeout storms,
    rate-limit storms, database contention, shutdown/restart under load, and
    resource-leak checks are bounded and reproducible.
  - Verification: dedicated stress matrix on Node 18.20.8 and 24.21.0.
  - Depends on: T02–T07.
  - Scope: L, split into focused test slices.
  - Outcome: `src/test/stress.test.ts`, 16 scenarios, all bounded and with no
    wall-clock thresholds — 100/1K concurrency (both the shed and the
    under-cap path), large payload, oversized payload, large search, provider
    timeout storm, rate-limit storm in-process and over HTTP, quota storm,
    database contention, shutdown under load, restart under load, file-descriptor
    leak, and metric cardinality. **It found a real defect:** `QuotaRateLimiter`
    separated check from charge with an `await`, so a burst of concurrent
    requests all observed an empty window — a 500-request storm against an
    organization cap of 20 served all 500. A rate limiter bypassable by sending
    requests in parallel is not a rate limiter; decide-and-charge is now
    serialized, with three regression tests.

## Checkpoints

- [ ] After T03: existing authentication, rate-limit, and security suites remain
  green; no public identity field can select a quota identity.
- [ ] After T06: health/metrics/logging contracts are documented and bounded.
- [ ] After T08: stress/resource evidence is recorded on both supported Node
  runtimes.
- [ ] No V5.2 distributed/runtime implementation starts before T09 passes.

## Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Abstraction changes auth order or identity semantics | Critical | Preserve current flow and run permanent SEC-RL/SEC-AUTH regressions |
| Metrics/logs create high-cardinality or secret leakage | High | Central bounded labels/redaction and adversarial tests |
| Health checks become expensive or expose internals | High | Cheap liveness, bounded dependency probes, public response allowlists |
| Shutdown hangs or drops active writes | High | Deadline, idempotent phases, drain tests, retained recovery state |
| Premature Redis/distributed coupling | High | Keep V5.1 interfaces implementation-neutral; defer Redis to V5.2 |

## Open Questions

- Which quota dimensions are enabled by default in the first V5.1 release?
  Default: preserve the current global/IP/API-key behavior and add tenant/user/
  agent dimensions only when trusted host context is present.
- Should provider health be queried synchronously on readiness? Default: use
  bounded cached/provider capability state and never require optional provider
  keys for local readiness.
