# Implementation Plan: V4.9.0 API, SDK & Compatibility Stabilization

## Overview

Prepare Remembra's public surfaces for V5 by introducing an explicit versioned
HTTP contract, a first-class TypeScript client, and stable MCP/provider
compatibility guarantees. Existing unversioned HTTP routes and current MCP tool
names remain supported throughout V4.9.

## Assumptions and boundaries

- V4.9 is additive: no existing route, tool, error envelope, or single-item
  service method is removed or silently reshaped.
- `/api/v1/*` is the canonical new HTTP namespace; legacy routes remain
  aliases until a later major release.
- The TypeScript SDK is fetch-based and has no runtime dependency on the
  server implementation. It targets Node 18.14.1+ and browsers with `fetch`.
  V4.9 publishes it at `@hilbras/remembra/sdk`; the package root remains the
  existing CLI entrypoint until a separately tested CLI/library split.
- Trusted agent context remains server-side. The SDK may send an API key, but
  it must never accept or synthesize a trusted `agentId` from a public field.
- Provider adapter work follows the existing bounded `providerFetch` policy;
  no new vendor SDK is introduced without a separate compatibility decision.
- This plan is separate from the completed V4.8 plan; V4.8 files remain the
  historical record and are not overwritten.

## Capability Map

| Module | Responsibility | Depends on |
|---|---|---|
| `api-v1` | Versioned HTTP path normalization, headers, and contract tests | — |
| `http-sdk` | First-class typed fetch client over `api-v1` | `api-v1` |
| `mcp-stable` | Stable tool manifest and compatibility aliases | `api-v1` |
| `provider-compat` | Vendor-neutral provider adapter boundary | — |
| `docs-v49` | SDK/API/migration/troubleshooting documentation | `http-sdk`, `mcp-stable` |

Build order: `api-v1` → `http-sdk` → `mcp-stable` → `provider-compat` →
`docs-v49`.

## Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| v1 aliases drift from legacy handlers | High | Route normalization plus parity tests; no duplicated business logic |
| SDK import starts CLI side effects | High | Separate SDK entrypoint and package export smoke test |
| MCP renames break existing clients | High | Keep old names; add explicit aliases and manifest tests |
| Agent identity is spoofed through SDK | Critical | SDK sends only API key; trusted resolver remains server-side |
| Provider abstraction expands scope | Medium | Define interfaces and adapters incrementally; preserve env behavior |
| Documentation drifts from code | Medium | Compatibility matrix and release checklist link code contracts to docs |

## Open Questions

- Should `/api/v1` become the default in the V4.9 README while legacy routes
  remain documented as compatibility aliases? Default: yes, without redirecting
  or removing legacy paths.
- Should the SDK be published at the package root or only at
  `@hilbras/remembra/sdk` first? **V4.9 decision:** use the side-effect-free
  `/sdk` and `/providers` subpaths; retain the root CLI export for backwards
  compatibility. A root library export requires a separately tested CLI/library
  split.
- Which provider adapter is the first external reference implementation after
  the interface lands? Default: OpenAI-compatible, because it is already the
  broadest existing HTTP contract.
