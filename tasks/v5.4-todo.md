# V5.4.0 Task List: Developer Platform

Status: planning started after the V5.0.3 release. V5.1–V5.3 remain
unfinished; this phase is additive and does not claim their distributed
capabilities. V5.5 and V6 remain out of scope.

Source plan: [`v5.4-plan.md`](v5.4-plan.md)

## Phase 0: Audit and contracts

- [x] **V5.4-T01 — Audit developer-platform surfaces**
  - Acceptance: API, SDK, batch, webhook, Python, OpenAPI, examples, and
      compatibility gaps are recorded before implementation.
  - Verify: source audit, endpoint inventory, and clean package smoke tests.
  - Depends on: V5.0.3 release.
  - Progress: the audit confirmed `/api/v1` compatibility, partial TypeScript
    SDK/batch support, and missing Python/webhook/OpenAPI/example surfaces.

  - Depends on: V5.4-T02.
  - Progress: typed snapshot create/restore methods, bounded client timeout,
    request-ID propagation, typed network-error normalization, opt-in read-only
    retries, and stable opaque cursor pagination are implemented and tested.

## Phase 2: Batch and events

- [x] **V5.4-T04 — Freeze batch API semantics**
  - Acceptance: limits, partial outcomes, idempotency, and transaction policy
      are explicit across service, HTTP, and SDK.
  - Verify: boundary, duplicate, retry, and partial-failure tests.
  - Depends on: V5.4-T02, V5.4-T03.
  - Progress: batch responses expose explicit per-item/read-only execution
    metadata; per-item errors use the public sanitizer; a transactional SQLite
    `Idempotency-Key` ledger with current-authorization preflight/recheck,
    stable credential/tenant/agent scope, integrity-protected rows and
    generation metadata, non-expiring replay claims, capacity limits, and a
    durable restore-pending gate replays completed mutation responses and fails
    closed on ambiguity. Bounded read-only search uses authorized single-search
    fan-out, per-item tenant revalidation, ordered outcomes, cancellation,
    embedding-free output, a 1,000-result aggregate budget, and incremental
    10 MiB response accounting across service, HTTP, MCP, and SDK. Final review
    follow-up also closes forged-tenant, missing-credential-scope, stale
    recovery, restore-publication, in-flight claim, ledger replacement, and
    deterministic capacity paths. Public batch embedding has a fixed V5.4 limit
    of zero until provider-cost, quota, and response-output policy decisions
    exist. Second-review follow-up attributes the durable gate to its owner (a
    data restore is completed by `recover verify`; an interrupted tenant
    migration is resumed by `migrate apply` and refuses verification
    publication), rejects an unsafe gate marker before any claim history is
    dropped, binds a released claim to its operation instead of freeing the key,
    migrates an older ledger in place after verifying every row, keeps a
    transient recovery read error local to one write, and keeps read-only
    batches off the writable-state channel. The SDK additionally rejects an
    impossible batch locally. Closure gates pass on Node 18.20.8 and 24.21.0:
    527 full-suite, 102 security, 52 recovery, and 36 documentation checks, 0
    production audit vulnerabilities, and a 231-file package dry run (482.0 kB
    packed). A pre-existing native SQLite teardown abort in the pinned
    `better-sqlite3` 11.x binding is contained by re-running only the aborted
    files, documented in `docs/troubleshooting.md`.

- [ ] **V5.4-T05 — Add signed webhook delivery**
  - Acceptance: HMAC, timestamp/replay protection, redacted payloads, bounded
      retries, and durable delivery state are implemented and tested.
  - Verify: signature/tamper/replay/retry/leak tests.
  - Depends on: V5.4-T01, V5.4-T04.
  - Progress: the delivery slice is implemented and tested. `@hilbras/remembra/webhooks`
    exports the event contract, an allowlist-only payload builder, HMAC-SHA256
    `t,v1` signing with a bounded timestamp window, a receiver replay guard, an
    integrity-protected durable SQLite queue, and a bounded exponential-backoff
    dispatcher with an injectable transport. Deliveries are notifications: a
    failed or missing dispatcher never fails, delays, or rolls back the write
    that produced the event. The full event set is emitted by the service, job
    outcomes flow through a new bounded `onSettled` queue callback that passes
    identifiers and types only, and `REMEMBRA_WEBHOOKS` plus
    `REMEMBRA_WEBHOOK_INTERVAL_MS` configure delivery for a deployment while
    HTTP and MCP processes drain due deliveries on a bounded interval. 19 new
    tests cover signature, tamper, timestamp, replay, payload redaction,
    durability, capacity, retries, configuration, and secret hygiene.
