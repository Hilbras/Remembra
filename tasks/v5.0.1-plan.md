# V5.0.1 Implementation Plan: Critical Security and Correctness Hotfixes

## Overview

V5.0.1 is the first post-V5 stabilization release. It addresses the confirmed
security and data-integrity risks identified in
[`REMEMBRA_V5_TO_V6_ROADMAP.md`](../REMEMBRA_V5_TO_V6_ROADMAP.md) before any
distributed-runtime or V6 work begins.

The release is intentionally narrow. It does not add new product features,
change the V5 public API, or begin the V6 architecture. Every change must
reduce a confirmed risk, preserve V5.9/V4.9 compatibility where promised, and
leave a permanent regression test.

## Audit findings

| ID | Finding | Severity | Current status |
|---|---|---:|---|
| `SEC-RL-001` | Rate limiting runs before authentication; invalid/anonymous requests can consume the configured key bucket. | High | Confirmed |
| `SEC-RL-002` | Rate identity is derived from the raw configured API key rather than a safe client/tenant identity. | High | Confirmed |
| `SEC-LOG-001` | Rate-limit and debug/provider paths can emit raw API keys, bearer values, or secret-bearing error text. | Critical | Confirmed |
| `SEC-STORAGE-001` | CLI silently falls back from SQLite to the file backend on initialization failure. | Critical | Confirmed |
| `SEC-PATH-001` | File history paths are built from unvalidated memory IDs and do not fully defend against traversal/symlink redirection. | Critical | Confirmed |
| `SEC-SNAPSHOT-001` | Strict tenant-scoped import can accept a signed tenantless snapshot and synthesize the current tenant. | Critical | Confirmed |
| `SEC-TENANT-001` | Existing cross-tenant paths are tested, but the new hotfix paths need permanent regression coverage. | High | Coverage gap |

## Non-goals for V5.0.1

- No V6 schema, policy engine, distributed runtime, Redis, PostgreSQL, or
  provider-independent redesign.
- No new public memory type or breaking route/tool change.
- No silent fallback that hides a storage failure.
- No migration-mode shortcut that lets ordinary snapshot restore assign a
  tenant.
- No release/tag/npm publication until all hotfix gates pass.

## Architecture decisions

1. **Authentication precedes rate consumption.** Public health/UI routes retain
   their explicitly documented exemptions; protected routes authenticate before
   consuming an authenticated bucket.
2. **Rate identities are opaque.** Raw API keys never become limiter keys or
   log fields. A safe key fingerprint, client identity, or trusted tenant
   identity is used instead.
3. **Central logging redacts secrets.** Field names, nested values, and
   secret-bearing messages are sanitized at the logging boundary, not only at
   individual call sites.
4. **SQLite failure is fail-closed by default.** File fallback requires an
   explicit compatibility flag, emits a warning, and is visible in health
   output.
5. **Filesystem paths are allowlisted and contained.** History paths validate
   IDs, resolve beneath the selected root, reject symlinks, and distinguish
   missing history from unsafe or unreadable history.
6. **Tenant assignment is explicit.** Ordinary strict restore accepts only
   snapshots whose tenant metadata matches the trusted destination. Tenantless
   data requires a separate explicit migration workflow.
7. **Tests are release assets.** Roadmap IDs are permanent regression names and
   are included in the security/release matrix.

## Dependency order

```text
audit + failing reproductions
        ↓
auth/rate isolation
        ↓
central log redaction
        ↓
storage startup fail-closed
        ↓
history path containment
        ↓
strict snapshot import rule
        ↓
full security/recovery/compatibility matrix
        ↓
5.0.1 release
```

The order follows the highest-risk boundaries first while keeping each slice
small enough to test and commit independently.

basic validation and authentication before consuming an authenticated rate
bucket. Preserve explicit public-route behavior.

**Acceptance criteria:**

  protected bucket.
- [ ] Valid credentials are authenticated before the protected rate check.
- [ ] Trusted identity/tenant resolution remains after authentication and

- [ ] Public health/UI/CORS behavior remains deliberate and tested.
- [ ] `SEC-RL-001` passes.

## Checkpoints and stop conditions

Stop the release and do not publish if any of the following occurs:

- a V5.0.1 security test is skipped, deleted, or weakened;
- SQLite failure can silently switch data planes;
- a raw secret appears in logs, limiter state, or test output;
- a strict tenant restore can assign tenantless data implicitly;
- history traversal/symlink fixtures disclose or modify data outside the root;
- a migration cannot be resumed, verified, or rolled back;
- full tests, build, audit, package, or supported Node checks fail;
- release artifacts do not point to one commit.

## Parallelization opportunities

After T01 and the failing reproductions:

- log-redaction implementation and startup-backend tests can proceed in
  separate commits after the shared logging contract is agreed;
- history path tests and snapshot tenant tests can proceed independently;
- documentation can be updated after behavior stabilizes;
- release preparation must remain sequential after all code/security gates.

## Definition of done

- [ ] All confirmed V5.0.1 findings are fixed or explicitly deferred with
      maintainer approval and a follow-up version.
- [ ] Permanent security regression IDs pass.
- [ ] V5 compatibility and legacy behavior remain covered.
- [ ] Security review, full tests, build, audit, package, and Node gates pass.
- [ ] Documentation and migration guidance match the implementation.
- [ ] V5.0.1 release artifacts are verified and published.
