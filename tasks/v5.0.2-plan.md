# V5.0.2 Implementation Plan: Security Consistency and Policy Hardening

## Overview

V5.0.2 is the next stabilization release after the V5.0.1 security hotfix. It
turns the existing tenant contract into an explicit, testable authorization
boundary for organization, project, user, and agent identities; centralizes
permission decisions; corrects encryption documentation; and finalizes the V5
threat model.

This release is intentionally narrower than V5.1 and V6. It does not introduce
Redis/PostgreSQL/distributed infrastructure, a new provider architecture, a new
memory type, or V6 policy/schema code.

## Capability map

| Module ID | Responsibility | Depends on |
|---|---|---|
| `identity-isolation` | Define and enforce effective organization/project/user/agent visibility | V5.0.1 tenant context and directory |
| `authorization-policy` | Pure permission/decision layer and service-boundary enforcement | `identity-isolation` |
| `provider-boundary` | Preserve and document public/internal provider-error separation | V5.0.1 redaction work |
| `encryption-docs` | State exactly which data planes encryption covers | existing `src/crypto.ts` behavior |
| `threat-model` | Final V5 assets, boundaries, threats, controls, residual risks | all V5.0.2 audit findings |

Build order is `identity-isolation` → `authorization-policy` → transport/service
integration → provider/encryption documentation → threat model → release gate.
Documentation audits may run in parallel after the implementation contract is
fixed.

## Security decisions

These decisions make implicit V5 behavior explicit without changing the V4.9
legacy mode contract:

1. **Organization is always the root boundary.** Strict operations require an
   exact organization match before any optional dimension is considered.
2. **Optional dimensions are conjunctive constraints.** If a trusted principal
   carries `projectId`, `userId`, or `agentId`, a candidate must satisfy that
   dimension. An absent optional dimension never means “all projects/users/
   agents.” A record with no optional dimension is visible only to an explicitly
   authorized organization-wide principal.
3. **User and agent are not inferred.** `provenance.agentId` remains attribution
   metadata and is never an authorization selector. Only the host-minted
   principal's `agentId` is authoritative.
4. **Capabilities are explicit.** Organization-wide reads/writes require an
   existing trusted tenant capability. Administrative export/management is a
   separate capability and is never inferred from a scope string or a client
   field.
5. **Deny wins and errors are non-informative.** Missing, stale, malformed, or
   unauthorized principals fail closed. Cross-tenant and unauthorized resource
   lookups retain the existing not-found semantics rather than confirming that
   an ID exists elsewhere.
6. **One decision path.** HTTP, MCP, SDK-facing service calls, batches, jobs,
   snapshots, and direct service methods use the same authorization decision
   function. Endpoints must not grow independent ad-hoc authorization branches.
7. **Provider errors remain split.** Public errors use stable generic codes and
   messages; internal diagnostics are bounded and redacted. This is a regression
   requirement, not a new provider feature.
8. **Encryption is described by data plane.** File-backed memory/history,
   snapshots, SQLite, and transport have separate guarantees. Setting
   `REMEMBRA_ENCRYPT_KEY` must not be described as SQLite or transport
   encryption.

## Planned contract

### Identity and visibility

The existing opaque `TenantContext` remains the public host boundary. The
implementation may add internal, immutable decision inputs, but public request
payloads cannot construct or override them. The effective visibility predicate
is the intersection of:

```text
organization match
+ project selector/capability
+ user selector/capability
+ agent selector/capability
+ existing owner/access/trust/lifecycle rules
```

Storage predicates remain ahead of candidate limits, counts, ranking, and
serialization wherever the current backend contract permits. A service-level
post-filter is not a substitute for tenant filtering in a backend query.

### Central authorization

A small pure module will define closed operation classes and permissions such as:

```text
memory.read
memory.write
memory.update
memory.delete
memory.search
memory.history
snapshot.create
snapshot.restore
tenant.manage
project.manage
```

The evaluator returns a typed allow/deny decision with a bounded, non-sensitive
reason code. It has no I/O and does not inspect memory content. Callers provide
the trusted principal, requested operation, and resource metadata. The service
performs the decision before provider calls, mutations, snapshot writes, or
backend operations that could reveal data.

Existing V5 capabilities and route names remain additive/compatible. Missing
new configuration fails closed in strict mode; legacy mode retains its explicit
V4 behavior and never silently acquires a strict policy.

## Tasks

### Phase 0: Audit and contract

- [ ] **V5.0.2-T01 — Audit current identity and authorization paths**
  - Record every service, HTTP, MCP, SDK, batch, job, snapshot, and direct
    backend path that consumes a tenant context.
  - Reproduce any user/agent/project visibility gaps before changing code.
  - Verify the V5.0.1 regression matrix remains green.

### Phase 1: Identity isolation

- [ ] **V5.0.2-T02 — Make user/agent/project visibility explicit**
  - Add the contract and implementation for conjunctive optional dimensions and
    explicit organization-wide capabilities.
  - Reject ambiguous/malformed host contexts and preserve legacy mode.
  - Add file and SQLite coverage for point reads, search/candidates, context,
    history, relations, and export.

### Phase 2: Central policy

- [ ] **V5.0.2-T03 — Add a pure centralized authorization evaluator**
  - Define typed operation/permission decisions, capability mapping, and safe
    reason codes.
  - Unit-test allow/deny/default-deny, stale membership, and dimension
    intersection cases.
  - Do not expose content or provider diagnostics in decisions.

- [ ] **V5.0.2-T04 — Route protected operations through the evaluator**
  - Integrate service methods first, then HTTP/MCP/SDK/batch/job/snapshot
    adapters.
  - Ensure authorization occurs before provider/network work and before writes.
  - Keep cross-tenant lookup behavior non-informative and preserve V4.9 legacy
    compatibility.

### Phase 3: Documentation and threat model

- [ ] **V5.0.2-T05 — Correct encryption and provider documentation**
  - Separate file memory/history encryption, snapshot handling, SQLite, and
    transport guarantees.
  - Document generic public provider errors and sanitized internal diagnostics.
  - Link the contracts from README, security, self-hosting, API, and migration
    documentation where relevant.

- [ ] **V5.0.2-T06 — Finalize the V5 threat model**
  - Change the threat model from draft to finalized.
  - Include assets, trust boundaries, attackers, attack surfaces, mitigations,
    residual risks, operator responsibilities, and evidence links.

### Phase 4: Release

- [ ] **V5.0.2-T07 — Run the V5.0.2 release gate**
  - Run build, full tests, permanent security/recovery matrices, docs check,
    audit, package dry-run, and tenant/scale benchmarks on Node 18.20.8 and
    Node 24.21.0.
  - Update version/changelog/README/release notes only after all gates pass.
  - Tag, publish, create the GitHub Release, and verify a clean installed
    package before moving to V5.0.3.

## Permanent regression candidates

- `SEC-AUTH-001`: user and agent selectors cannot widen visibility.
- `SEC-AUTH-002`: missing capabilities and ambiguous principals fail closed.
- `SEC-AUTH-003`: every protected service/transport path uses the central
  evaluator and denies before provider/write side effects.
- `SEC-AUTH-004`: cross-tenant and unauthorized lookups remain
  indistinguishable from missing resources.
- `SEC-AUTH-005`: public provider errors expose no internal diagnostics.
- `SEC-DOC-001`: encryption documentation matches the implemented data planes.

The final IDs and exact test names are recorded in the task checklist after the
audit; existing `SEC-RL-*`, `SEC-LOG-*`, `SEC-STORAGE-001`, `SEC-PATH-001`,
`SEC-SNAPSHOT-001`, and `SEC-TENANT-001` remain permanent.

## Non-goals and stop conditions

- No V5.0.3 recovery state-machine work.
- No V5.1 distributed runtime or rate-limiter abstraction.
- No V5.5+ full RBAC/product policy engine.
- No V6 policy, schema, provider, API, or migration implementation.
- No silent legacy-to-strict transition.
- No release if any critical/high audit finding, skipped security regression,
  cross-tenant leak, or provider diagnostic leak remains.

## Assumptions to validate during audit

1. Existing `TenantContext` capabilities are the trusted source for V5.0.2;
   V5.0.2 adds internal permission mapping, not a new identity provider.
2. A host that needs organization-wide access must mint an explicit capability;
   a project/user/agent selector alone never implies that access.
3. Existing owner/access/trust/lifecycle predicates remain authoritative after
   the new identity dimensions.
4. Provider error sanitization from V5.0.1 is already implemented and needs
   regression/documentation rather than a redesign.
5. `REMEMBRA_ENCRYPT_KEY` encrypts the file backend's memory/history payloads;
   it does not encrypt SQLite pages or HTTP transport.

These assumptions will be corrected in this plan if the code audit finds a
different existing contract.
