# V5.0.3 Implementation Plan: Reliability and Recovery Hardening

## Overview

V5.0.3 is the bounded reliability release after V5.0.2 authorization hardening.
It makes startup validation, readiness, recovery state, snapshot validation, and
atomic restore behavior deterministic and testable. It preserves V4.9/V5
compatibility and does not begin the V5.1 distributed runtime or V6 work.

## Roadmap capability map

| Capability | Outcome | Depends on |
|---|---|---|
| `startup-validation` | Validate configuration, storage, schema, encryption, tenant, and filesystem safety before serving | V5.0.2 |
| `recovery-state` | Expose deterministic Healthy/Degraded/Recovering/Failed/ReadOnly states | startup validation |
| `snapshot-validation` | Validate format/version/integrity/metadata/tenant/schema/relations/timestamps before mutation | V5.0.1/V5.0.2 snapshot contracts |
| `atomic-recovery` | Prepare, stage, commit, verify, and roll back without partial primary overwrite | startup + snapshot validation |
| `failure-regressions` | Permanent crash/corruption/permission/partial-restore tests | all above |

## Safety decisions

1. Invalid startup state fails closed; a storage error is never hidden by a
   silent backend switch.
2. Readiness has one deterministic state vocabulary: `Healthy`, `Degraded`,
   `Recovering`, `Failed`, or `ReadOnly`. Public health may expose bounded
   details, never memory content or secrets.
3. Snapshot and backup validation completes before primary-store mutation.
4. Restore uses a staged/verified commit protocol with an explicit rollback or
   retained previous copy.
5. Interrupted operations are resumable or explicitly reported as partial;
   they are never reported as successful.
6. Recovery tests use temporary roots and injectable filesystem/database
   failures; they do not depend on host disk-full conditions.
7. V5.0.2 authorization, tenant, path, rate-limit, and provider regressions
   remain mandatory on every V5.0.3 gate.

## Candidate permanent regressions

- `REC-START-001`: invalid storage/configuration fails before serving.
- `REC-STATE-001`: readiness transitions are deterministic and bounded.
- `REC-SNAP-001`: malformed/mismatched snapshots are rejected before writes.
- `REC-ATOMIC-001`: interrupted restore never replaces the primary store with
  an unverified partial state.
- `REC-CRASH-001`: crash/resume and rollback retain a verified previous copy.
- `REC-FAIL-001`: permission, corruption, and filesystem failures are
  explicit and do not silently fall back.

## Non-goals and stop conditions

- No V5.1 rate-limiter abstraction, Redis/PostgreSQL, distributed runtime, or
  provider architecture.
- No V5.2+ infrastructure or V5.5 full policy engine.
- No V6 implementation.
- No release while a critical/high recovery finding, skipped security
  regression, or ambiguous health state remains.
