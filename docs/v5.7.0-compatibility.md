## Preserved contracts

- **No new runtime dependency.** Still four: `@modelcontextprotocol/sdk`,
  `better-sqlite3`, `yaml`, `zod`. `redis` remains an **optional peer** and is not
  even a devDependency.
- **No new subpath.** All six published subpaths from 5.6.0 are unchanged and still
  import independently.
- **No removed export.** Every export present in 5.6.0 is still present. Nothing
  in the HTTP, MCP or SDK contract was removed or renamed.
- **`/health/ready` is byte-identical to 5.6.0.** Nothing in this milestone touched
  the readiness payload, the shared-state configuration, or the distributed paths.
- **Security boundaries are untouched.** Auth-before-rate-limit, opaque tenant
  identities, centralized redaction, sanitized errors, path containment, strict
  snapshots and fail-closed recovery are all unchanged and all still covered by the
  142-case security matrix and the 52-case recovery matrix.

## Two default-on behaviour changes

Everything else in this release is additive with unchanged defaults. These two are
not, and they are the whole compatibility surface.

### 1. Exact duplicate results are collapsed by default

Two records of the same statement are one answer to a question; returning both
spends context on a repeat. Byte-identical text is now collapsed.

- Escape hatch: `dedupeExact: false`, or `?dedupeExact=false` over HTTP.
- **Same-source collapsing is off by default** and is a separate flag
  (`dedupeSameSource`). Identical text from two *different* sources is often
  corroboration rather than duplication, and discarding the second source is a
  worse error than showing a repeat.
- Nothing is deleted. This affects a result set; the store still holds every copy
  and each is readable by id.

### 2. Superseded memories are excluded by default

A query for the current policy no longer returns v1 and v2 side by side, which the
V5.7.0 audit reproduced.

- Escape hatch: `includeSuperseded: true`, or `?includeSuperseded=true`.
- Suppression applies **only when the superseding memory is actually available** in
  the candidate set, so a dangling `supersededBy` keeps the old copy visible rather
  than replacing it with nothing. Chains resolve to the newest link.
- Nothing is deleted. "What did this used to say?" is a real question, which is why
  the flag exists.

If either default is wrong for your workload, both are one query parameter away
and neither requires a redeploy.

## Ranking quality changed, by design

Three changes alter which memories rank where. None of them is configurable away,
because they are fixes rather than knobs:

- **Real inverse document frequency.** The old "idf" factor was computed from *the
  document being scored*, so it was a coverage discount wearing the name of IDF and
  could not tell a rare term from a common one.
- **Whole-token matching, phrase scoring and field weights.** A query for `cat`
  scored `"concatenate the streams"` at exactly the same 60.00 as `"the cat sat"`,
  because matching was a single `String.includes`. A tag mention no longer counts
  the same as prose.
- **Fusion weights are configurable** with defaults that reproduce the previous
  behaviour exactly, so an unconfigured deployment ranks identically.

## Known limitations

- **Non-ASCII queries return no lexical results.** `extractQuery` filters query
  terms with `/^[a-z0-9]+$/u`, so a query in any non-ASCII script produces zero
  terms and retrieval falls back to the vector path alone — nothing at all when no
  embedding provider is configured. The CJK branch in `tokenize` is therefore
  unreachable from the query path: it looks like support and is not. Documents in
  those scripts are stored and tokenised correctly; querying is what is affected.
  Not fixed here because the one-line change alters what existing deployments get
  back for non-ASCII input. Full analysis in `docs/v5.7.0-audit.md` (S7).
