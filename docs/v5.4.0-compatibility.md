# V5.4.0 compatibility report

**Status:** Candidate. Every gate below was executed on the release commit.
**Base:** V5.0.3 (the last published release).
**Scope:** Developer platform only — versioned API metadata, hardened SDKs,
frozen batch semantics, signed webhooks, and developer documentation.

## 1. What is new

| Area | Addition | Compatibility impact |
|---|---|---|
| API metadata | `GET /api/v1/capabilities`, `X-Remembra-API-Version` | Additive; legacy routes and response bodies unchanged |
| TypeScript SDK | Snapshot methods, bounded timeouts, request IDs, typed errors, read-only retries, opaque cursor pagination, batch budget guard | Additive; existing methods keep their signatures |
| Batch contract | Explicit execution metadata, bounded read-only search, `Idempotency-Key` with a durable claim ledger | New optional header; no existing route changes shape |
| Webhooks | `@hilbras/remembra/webhooks` with HMAC signing, replay guard, durable delivery state | Opt-in via `REMEMBRA_WEBHOOKS`; disabled by default |
| Python SDK | `hilbras-remembra` with sync and async clients | New package; targets the same `/api/v1` contract |
| Documentation | OpenAPI 3.1 spec, example suite, Python and examples guides | Additive |

## 2. What is unchanged

These V4.9/V5.0.3 guarantees are asserted by the permanent regression suites and
were re-executed for this release:

- Authentication runs before rate limiting, and rate-limit identities are never
  the server secret.
- API keys, bearer tokens, and provider secrets never appear in logs; redaction
  is centralized.
- An inaccessible id returns `NOT_FOUND` rather than disclosing existence.
- History paths are validated, normalized, and contained; traversal, null
  bytes, separators, and symlinks are rejected.
- Tenant-scoped snapshot imports never assign tenantless records silently;
  migration requires an explicit signed plan.
- Provider errors are separated into internal diagnostics and a sanitized
  public error.
- Recovery is deterministic: `Healthy`, `Degraded`, `Recovering`, `Failed`,
  `ReadOnly`, with durable, atomically replaced state.
- Snapshot restore is preflighted, transactional, and restart-safe.
- Optional providers stay optional, and file fallback still requires
  `REMEMBRA_ALLOW_FILE_FALLBACK=1`.

## 3. Deliberate non-claims

V5.4.0 does **not** deliver, and its documentation does not claim:

- distributed quotas, distributed rate limiting, or a Redis-backed limiter
  (V5.1 is unfinished);
- distributed jobs, workers, or distributed locking (V5.2 is unfinished);
- the advanced retrieval engine, hybrid ranking, or reranking (V5.3 is
  unfinished);
- any V5.5 tenancy/RBAC work or V6 runtime change;
- a public batch embedding operation, which has a fixed limit of zero in V5.4;
- distributed webhook workers or a subscription management API.

Delivery state, the idempotency ledger, and webhook dispatch are single-host and
durable on local disk. That is an explicit boundary, not an oversight.

## 6. Migration guidance

No action is required to upgrade from V5.0.3.

- Existing HTTP clients keep working: `/api/v1` paths, legacy routes, and
  response bodies are unchanged.
- New headers are optional. `X-Remembra-API-Version` and `X-Remembra-Request-Id`
  can be ignored.
- `Idempotency-Key` is accepted only on `POST /api/v1/memories/batch`. A host
  that authenticates without a static API key must provide a post-authentication
  credential scope for keyed requests.
- Webhooks are off unless `REMEMBRA_WEBHOOKS` is set, and enabling them cannot
  change the outcome of a write.
- New directories appear only when their feature is used:
  `<REMEMBRA_HOME>/.webhooks`.

## 7. Known limitations

1. The native SQLite binding can abort a test process during environment
   teardown after all assertions have passed. The gates re-run only the aborted
   files, log every recovery, and still fail immediately on any real failure.
2. Webhook delivery is in-process. A crash between queueing and delivery leaves
   the row durable, and the next process drains it.
3. Batch idempotency claims never expire. Reusing a key for a different request
   is a `CONFLICT` until an operator invalidates the ledger, which is the safe
   direction.
