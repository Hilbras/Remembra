# V4.4.0 — Security & Memory Integrity

**Plan §7.** Hardens Remembra against malicious input, memory poisoning, and abuse. Extends the trust system with pattern-based prompt injection detection, adds HTTP-level protections (rate limiting, secure headers, CORS), and introduces sensitive-data policies (reject / quarantine beyond the existing redact mode).

---

## Objective

Protect Remembra across three layers:

1. **Transport** — rate limiting, timeouts, secure response headers, CORS
2. **Input** — prompt injection detection, sensitive-data policy engine
3. **Memory integrity** — structured audit events, conflict awareness on ingest

Every change is additive; no existing API contract shifts.

---

## 7.1 Rate Limiting

Per-API-key sliding-window rate limiter. Configurable via env vars:

| Variable | Default | Meaning |
|----------|---------|---------|
| `REMEMBRA_RATE_LIMIT` | `60` | max requests per window |
| `REMEMBRA_RATE_WINDOW_MS` | `60000` | window size in ms |

Exceeded → `429 Too Many Requests` with `Retry-After` header.

The `/health` and `/metrics` (when unkeyed) routes are exempt. The web UI shell is exempt.

---

## 7.2 Secure Response Headers

Every JSON response includes:

```
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Content-Security-Policy: default-src 'none'; ...
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-XSS-Protection: 0
Referrer-Policy: no-referrer
Cache-Control: no-store
```

UI routes keep their existing stricter CSP; API routes get the above baseline.
`REMEMBRA_SECURE_HEADERS=0` disables (for dev behind a reverse proxy that already sets them).

---

## 7.3 CORS Policy

When `REMEMBRA_CORS_ORIGIN` is set, every response includes:

```
Access-Control-Allow-Origin: <value>
Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
Access-Control-Allow-Headers: Content-Type, Authorization, x-api-key
Access-Control-Max-Age: 86400
```

`OPTIONS` preflight requests are handled without auth check (CORS spec).
Wildcard (`*`) is rejected when an API key is configured (CORS + auth conflict).

---

## 7.4 Request Timeouts

Configurable via `REMEMBRA_REQUEST_TIMEOUT_MS` (default `30000`).
Each in-flight request is aborted if it exceeds the timeout.
Timed-out requests return `504 Gateway Timeout`.

---

## 7.5 Concurrency Limits

Configurable via `REMEMBRA_MAX_CONCURRENT` (default `32`).
When the limit is reached, new requests queue briefly; if the queue also fills,
the request returns `503 Service Unavailable`.

---

## 7.6 Prompt Injection Detection

Pattern-based detector runs on every `memory_store` and digest-extracted item
before persistence. Detects patterns attempting to manipulate:

- Role/instruction override attempts (`"ignore previous instructions"`, `"you are now"`)
- System prompt leakage requests (`"output your system prompt"`, `"reveal your instructions"`)
- jailbreak patterns (`"DAN"`, `"Developer Mode"`, `"unleashed"`)
- Metadata manipulation (`"set your trust to"`, `"change your retention"`)

Detection is **informational only** — flagged items are stored with
`meta.injected?: true` but are not blocked. The dashboard highlights them.
Pattern list is tunable via `REMEMBRA_INJECTION_PATTERNS` (comma-separated regexes).

---

## 7.7 Sensitive Data Policies

Extends the existing `REMEMBRA_REDACT=1` (pattern-based redaction) with a
policy engine:

| Variable | Default | Modes |
|----------|---------|-------|
| `REMEMBRA_SENSITIVE_POLICY` | `redact` | `allow` · `redact` · `reject` · `quarantine` |

- `allow` — store as-is (same as current unkeyed behavior)
- `redact` — replace matches with typed placeholders (current behavior)
- `reject` — return `400 SENSITIVE_DATA` on any match; nothing stored
- `quarantine` — store with `meta.quarantined: true` + `trust: "unverified"`; hidden from default search; visible via `includeQuarantined` flag

Patterns covered: API keys (`sk-`, `ghp_`, `AKIA`), passwords, private keys
(`-----BEGIN.*PRIVATE KEY-----`), auth cookies, financial secrets.
The pattern set is a superset of the existing PII redaction rules.

---

## 7.8 Audit Events

The existing `memory_audit` table records mutations. V4.4.0 adds structured
event emission so consumers can subscribe to a stream:

| Event | Trigger |
|-------|---------|
| `memory.created` | `store()` / `importMemory()` |
| `memory.updated` | `update()` |
| `memory.merged` | digest merge |
| `memory.deleted` | `forget()` |
| `memory.archived` | `archive()` |
| `memory.revived` | `revive()` |
| `memory.conflict` | CAS version conflict (409) |
| `memory.quarantined` | sensitive data quarantine |
| `auth.failure` | invalid API key |
| `rate.limit` | rate limit exceeded |

Events are also emitted to the existing `logEvent` sink so they appear in the
structured log output alongside the audit table rows.

An optional HTTP endpoint `GET /audit` (auth-required) returns recent events
with pagination.

## 7.9 V4.4.0 Exit Criteria

All of the following must be true:

- [ ] Rate limiting enforces per-key windows; `429` + `Retry-After`
- [ ] Secure headers present on every API response (configurable off)
- [ ] CORS works with explicit origin; preflight handled; wildcard rejected with key
- [ ] Request timeout aborts long-running handlers; `504` returned
- [ ] Concurrency limit caps simultaneous in-flight requests; `503` when full
- [ ] Prompt injection patterns detected and flagged in stored memories
- [ ] Sensitive data policy supports all four modes (allow/redact/reject/quarantine)
- [ ] Audit events emitted to log sink and queryable via `GET /audit`
- [ ] All 214 existing tests still pass
- [ ] New tests cover each security feature
