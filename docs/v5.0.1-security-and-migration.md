# V5.0.1 Security and Migration Guide

**Status:** Unreleased hotfix documentation
**Scope:** Critical V5.0.1 security, storage, history, and tenant-snapshot migration changes.

V5.0.1 is a corrective release. It does not introduce V6 architecture or change
the V5 public API.

## Security changes

### Authentication precedes protected rate limiting

Protected HTTP routes now authenticate before consuming the protected rate
bucket. Invalid or anonymous requests use a separate address bucket, so an
attacker cannot consume a legitimate configured client's quota.

Rate identities are opaque fingerprints or trusted tenant dimensions. Raw API
keys are never stored in the rate limiter or emitted in logs.

### Central log redaction

Structured and text logs redact sensitive field names, nested headers,
authorization values, API keys, tokens, passwords, secrets, and common provider
credential patterns. Debug search and provider diagnostics receive the same
redaction treatment.

HTTP provider errors are generic public messages; internal diagnostics remain
in bounded server-side telemetry.

### SQLite startup fails closed

SQLite is the default backend. Initialization/schema/migration readiness failure
now stops startup instead of silently switching to the file backend.

A file backend is available only as an explicit compatibility fallback:

```bash
export REMEMBRA_ALLOW_FILE_FALLBACK=1
```

When enabled, startup emits a warning and health reports the selected backend:

```json
{
  "backend": "file",
  "fallback": true
}
```

Do not use the fallback to hide corruption or permission failures. It is a
compatibility switch, not a recovery strategy.

### History path containment

File-backed history validates memory IDs, resolves paths beneath the selected
root, rejects symlinked history directories/files/sidecars, and distinguishes a
missing history directory from an unsafe or unreadable one.

## Tenant snapshot safety

Ordinary restore is intentionally strict:

```text
strict tenant destination
        +
tenantless snapshot
        =
SNAPSHOT_INVALID
```

A signed snapshot must carry matching tenant metadata before ordinary preview or
import can write records. Project, user, and agent dimensions must match a
trusted scoped context when one is present.

Tenantless data is migrated only through the explicit plan/apply workflow.

## Migration workflow

All commands below run from the Remembra CLI. The plan and snapshot must be
stored with restrictive permissions because they contain memory metadata and
signed migration information.

### 1. Analyze

Analysis is read-only and requires the snapshot HMAC key:

```bash
export REMEMBRA_SNAPSHOT_KEY="$(openssl rand -hex 32)"
remembra migrate analyze snapshot.json
```

The report identifies tenantless/tenant-bound records, mixed input, source
organizations, schema version, estimated size, and whether explicit migration
is required.

### 2. Create a target-bound plan

Planning requires strict local operator binding. The target is derived from the
trusted environment, never from a public request field:

```bash
export REMEMBRA_TENANT_MODE=strict
export REMEMBRA_TENANT_ID=org-demo
export REMEMBRA_TENANT_MEMBERSHIP_VERSION=membership-42
export REMEMBRA_SNAPSHOT_KEY="$(openssl rand -hex 32)"

remembra migrate plan snapshot.json \
  --out migration-plan.json \
  --source-namespace legacy-root
```

The plan contains a signed manifest, source checksums, destination organization
mapping, and typed source/destination records. The plan file is written with
mode `0600`.

### 3. Dry run

Dry-run performs full signature, checksum, mapping, target, and backend
preflight without importing records:

```bash
remembra migrate apply snapshot.json \
  --plan migration-plan.json \
  --dry-run
```

### 4. Apply

```bash
remembra migrate apply snapshot.json \
  --plan migration-plan.json
```

The target must match `REMEMBRA_TENANT_ID`. Applying the same valid plan again
is idempotent: already-present destination records are reported as skipped.

### 5. Verify

After apply, export the destination and run normal authenticated verification:

```bash
remembra export destination-export.json
remembra import destination-export.json --dry-run
```

For production, also verify record counts, tenant membership, policy decisions,
relationships, history, audit events, and representative retrieval results.

## Failure and rollback

- A tampered snapshot, plan, manifest, or target is rejected before writes.
- A failed preflight leaves the destination unchanged.
- A failed/interrupted apply must be investigated with the migration state and a
  verified backup; do not rerun with a different target or unsigned plan.
- Restore the verified pre-migration backup using the documented SQLite/file
  recovery procedure before retrying.
- Never “fix” a failed migration by manually assigning tenant fields in a
  snapshot.
