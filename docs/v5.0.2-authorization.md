# V5.0.2 Authorization and Tenant-Isolation Contract

**Status:** Implemented for the V5.0.2 release line.

V5.0.2 keeps the V5.0.1 tenant boundary and makes its optional user/agent
dimensions explicit. The pure decision layer lives in
`src/authorization.ts`; storage backends apply the same effective-visibility
predicate before returning rows.

## Identity dimensions

A trusted `TenantContext` contains an organization and zero or more explicit
selectors:

```text
organizationId
projectId?
userId?
agentId?
```

The rules are conjunctive:

- Organization must always match.
- A selector carried by the principal must match the resource.
- A resource carrying a selector not carried by a scoped principal is hidden.
- A missing selector never means “all projects/users/agents.”
- An organization-wide principal has no optional selectors and must have
  explicit `tenant:read`/`tenant:write` capability as appropriate.
- `tenant:admin` does not erase explicit project/user/agent selectors.
- `provenance.agentId` is attribution only. It cannot authorize a persisted
  `Memory.agentId` or a tenant selector.
- Public HTTP, MCP, SDK, and snapshot inputs cannot construct a context.

Existing owner/access/trust/lifecycle rules remain additional predicates. A
central decision never widens them.

## Capability and operation matrix

| Operation | Required capability | Notes |
|---|---|---|
| `memory.read`, `memory.search`, `memory.history` | `tenant:read` | Exact resource dimensions are checked when a resource is known |
| `memory.write`, `memory.update`, `memory.delete` | `tenant:write` | `tenant:admin` satisfies data-plane writes |
| `snapshot.create` / full or selected export | `tenant:export` | Explicit; ordinary read is not export authority |
| `snapshot.restore` / ordinary import | `tenant:write` | Strict snapshots are signed and target-bound |
| `tenant.manage`, `project.manage` | `tenant:admin` | Organization administration; scoped admin selectors remain scoped |

The evaluator returns only an internal allow/deny decision and a bounded
reason code. Transport errors remain generic/non-informative. HTTP, MCP, and
service calls do not expose the reason code for a foreign resource.

## Membership freshness

Pure policy evaluation has no I/O. A configured `verifyTenantContext` callback
(or `TenantDirectory`) is checked by `MemoryService` before ordinary service
operations, queued work, and migration. A stale or revoked membership fails
closed before provider calls or writes.

The stock strict CLI binds one environment-provided operator context for the
process. A deployment that needs live revocation must provide a host-owned
membership verifier; environment membership versions alone are not a
distributed identity service.

## Storage and derived paths

The same filter is applied to:

- point reads, writes, archive/revive/forget;
- search candidates, counts, ranking, FTS, and context;
- history and references;
- entity visibility;
- batch export;
- snapshots and explicit migration;
- file history and SQLite auxiliary rows.

A direct backend filter is exact by default. Callers that intentionally need
organization-wide access must set `organizationWide: true` on the trusted
internal filter; an omitted flag does not silently widen user/agent access.

## Migration rule

A signed migration plan remains separate from ordinary restore. Every mapped
destination record must match the trusted destination filter before preflight
or import. A valid signature does not authorize a project/user/agent outside
the caller's scope.

## Compatibility

Legacy mode keeps V4.9 behavior and does not acquire V5 tenant semantics.
Strict mode is the only mode that accepts tenant data-plane operations. The
V5.0.2 changes are additive to the V5.0.1 public routes/tools; no V6 policy or
schema is introduced.
