# V4.3.0 — Storage & Index Architecture

**Plan §6.** Replaces the file-based `MemoryStore` with a SQLite-backed `SqliteBackend` while preserving every public API contract (`MemoryBackend`, HTTP endpoints, MCP tools, dashboard behavior). File storage becomes an export format; SQLite is the runtime engine.

---

## Objective

Separate memory semantics from physical storage:

- **Runtime:** SQLite with FTS5 + embedded vectors
- **Export:** human-readable Markdown (unchanged format)
- **Migration:** automatic file → SQLite on first launch; never requires manual intervention
- **Public API:** zero breaking changes — `MemoryBackend` interface, HTTP endpoints, MCP tool schemas, dashboard UX all identical

---

## Architecture

```
┌─────────────────────────────────────────────────┐
│  Transport (HTTP / MCP / CLI)                   │
├─────────────────────────────────────────────────┤
│  Service (MemoryService)                        │
│  — unchanged, talks only to MemoryBackend       │
├──────────────────┬──────────────────────────────┤
│  SqliteBackend   │  FileBackend (deprecated,    │
│  (default)       │   kept as export target)     │
├──────────────────┴──────────────────────────────┤
│  SQLite database (~/.remembra/data.sqlite)      │
│  ─ memories (main table)                        │
│  ─ memories_fts  (FTS5 virtual, synced)         │
│  ─ memory_versions                               │
│  ─ memory_audit                                  │
└─────────────────────────────────────────────────┘
```

## 6.1 Repository Abstraction

The existing `MemoryBackend` interface in `src/backend.ts` stays **unchanged**. A new `SqliteBackend` class implements it:

```ts
// src/sqlite-backend.ts
export class SqliteBackend implements MemoryBackend {
  constructor(private readonly db: Database);
  // implements all MemoryBackend methods
}
```

Optional observability hook (`cacheStats`) is replaced by SQLite-level stats exposed via `/health`:
- `db_size_bytes` — on-disk database size
- `memory_count` — active memories
- `archived_count` — archived memories
- `fts_available` — whether FTS5 is enabled

## 6.2 SQLite Schema

### Main table

```sql
CREATE TABLE memories (
  id                TEXT PRIMARY KEY,
  type              TEXT NOT NULL CHECK (type IN (
                      'fact','preference','decision','constraint',
                      'instruction','role','entity','relationship',
                      'event','history','observation'
                    )),
  content           TEXT NOT NULL,
  scope             TEXT NOT NULL DEFAULT 'global',
  tags              TEXT NOT NULL DEFAULT '[]',
  importance        INTEGER NOT NULL DEFAULT 3 CHECK (importance BETWEEN 1 AND 5),
  confidence        REAL NOT NULL DEFAULT 1.0 CHECK (confidence BETWEEN 0 AND 1),
  trust             TEXT NOT NULL DEFAULT 'trusted' CHECK (trust IN (
                      'system','verified','trusted','unverified'
                    )),
  provenance        TEXT NOT NULL,  -- JSON
  retention         TEXT NOT NULL DEFAULT 'decaying' CHECK (retention IN (
                      'pinned','persistent','ephemeral','decaying','neverExpire'
                    )),
  relations         TEXT NOT NULL DEFAULT '[]',  -- JSON array of {id, kind}
  version           INTEGER NOT NULL DEFAULT 1,
  created_at        TEXT NOT NULL,
  updated_at        TEXT NOT NULL,
  last_seen         TEXT,  -- NULL = never retrieved
  archived_at       TEXT,
  embedding         BLOB,  -- raw bytes of Float32Array
  embedding_model   TEXT,
  embedding_dim     INTEGER,
  embedding_version TEXT
);

-- Indexes
CREATE INDEX idx_memories_scope      ON memories(scope);
CREATE INDEX idx_memories_type       ON memories(type);
CREATE INDEX idx_memories_archived   ON memories(archived_at);
CREATE INDEX idx_memories_updated    ON memories(updated_at DESC);
CREATE INDEX idx_memories_last_seen  ON memories(last_seen);
```

### FTS5 virtual table

```sql
CREATE VIRTUAL TABLE memories_fts USING fts5(
  content,
  content_map = memories,
  content_rowid = rowid
);
```

Sync triggers keep FTS5 in step with DML:

```sql
CREATE TRIGGER memories_ai AFTER INSERT ON memories BEGIN
  INSERT INTO memories_fts(rowid, content) VALUES (new.rowid, new.content);
END;
CREATE TRIGGER memories_ad AFTER DELETE ON memories BEGIN
  INSERT INTO memories_fts(memories_fts, rowid, content) VALUES ('delete', old.rowid, old.content);
END;
CREATE TRIGGER memories_au AFTER UPDATE ON memories BEGIN
  UPDATE memories_fts SET content = new.content WHERE rowid = old.rowid;
END;
```

> **Fallback:** If the SQLite build lacks FTS5 support, the backend starts without the virtual table and falls back to keyword-only retrieval (the existing BM25-lite path). A startup warning is logged.

### Version history

```sql
CREATE TABLE memory_versions (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  memory_id  TEXT NOT NULL REFERENCES memories(id) ON DELETE CASCADE,
  content    TEXT NOT NULL,
  reason     TEXT,
  created_at TEXT NOT NULL
);
CREATE INDEX idx_versions_memory ON memory_versions(memory_id, created_at DESC);
```

### Audit log

```sql
CREATE TABLE memory_audit (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  memory_id  TEXT REFERENCES memories(id),
  action     TEXT NOT NULL CHECK (action IN (
                'store','update','archive','revive','forget','import'
              )),
  details    TEXT,  -- JSON
  created_at TEXT NOT NULL
);
CREATE INDEX idx_audit_memory ON memory_audit(memory_id, created_at DESC);
```

## 6.3 Full-Text Search

The FTS5 table serves as the keyword-match engine, replacing the file-system glob + string scanning used today:

| Operation | Old path | New path |
|-----------|----------|----------|
| Match terms against content | scan all `.md` files, string.includes per term | `SELECT ... FROM memories_fts WHERE memories_fts MATCH ?` |
|BM25-lite scoring | `keywordScore()` in JS | `rank(memories_fts, query)` with snippet output |
| No-embed fallback | loop over all files | FTS5 returns ranked IDs; JS layer still applies modifiers |

The retrieval pipeline (`src/retrieval.ts`) keeps its existing `keywordScore()` function as a **fallback** when FTS5 is unavailable (no-index mode). When FTS5 is present, the backend pre-filters candidates via FTS5 before the pipeline scores them — this avoids loading every memory into memory for keyword queries.

---

## 6.4 Vector Storage

Embeddings move from Markdown frontmatter into the `embedding BLOB` column:

- **Write path:** after `embedCached()` resolves, the returned `number[]` is typed into a `Float32Array`, converted to `Buffer`, and stored as the BLOB. Model/dim/version metadata go into their own columns.
- **Read path:** `embedding` is deserialized back to `number[]` (or `null` if absent). The retrieval pipeline treats it identically to the current in-memory array.
- **Backfill:** on first launch after migration, any memories without an embedding re-run the embedder (same as today's `maintain --backfill`).

## 6.5 Markdown Export

Markdown remains the human-readable, git-friendly format. Two new CLI commands:

```
remembra export-markdown <directory>   # dump all active memories as .md files
remembra import-markdown <directory>   # import .md files into the SQLite store
```

The `.md` format is **identical** to the v4.1.x flat-file layout (YAML frontmatter + body). This ensures round-trip compatibility with any tool that consumed the old files.

The `export` / `import` snapshot commands (JSON) continue to work unchanged.

---

## 6.6 Migration System

**Auto-migration on first launch:** when `SqliteBackend` detects no existing database but finds legacy `.md` files in the configured root, it:

1. Reads every `.md` file using the existing parser
2. Inserts each memory into SQLite
3. Populates FTS5, versions, and audit tables
4. Creates a `.legacy/` directory and moves the old tree there (never deletes immediately)
5. Logs a one-time warning: `"auto-migrated from flat files: N memories"`

**Manual migration:** `remembra migrate` runs the same steps explicitly (useful for diagnostics or re-migration).

**Migration validation:** after import, a row-count check compares source file count vs destination rows. A mismatch emits a warning but does not block.

**Never-edit requirement:** users must never manually edit the SQLite database. All mutations go through the backend API.

## 6.7 Backup / Restore

```
remembra backup <file>       # copies DB + writes <file>.sha256 sidecar
remembra restore <file>      # verifies sha256, replaces current DB atomically
```

Implementation:
- `backup`: `fs.copyFileSync(dbPath, tmp)` → compute SHA-256 → write `<file>.sha256` → rename to target
- `restore`: read sidecar hash → verify `sha256(file) === hash` → `fs.rename(tmp, dbPath)` (atomic on same filesystem)

The `POST /maintain` endpoint is unaffected. A new `POST /backup` endpoint is **not** added — backups are an admin CLI operation.

## 6.8 V4.3.0 Exit Criteria

Remembra must support, **without changing the public memory API**:

```
[ ] SQLite as primary runtime backend
[ ] FTS5 full-text search (with graceful fallback)
[ ] Vector storage in BLOB column (no more embeddings in frontmatter)
[ ] Automatic file→SQLite migration on first launch
[ ] Manual migration command (`remembra migrate`)
[ ] Markdown export (`remembra export-markdown`)
[ ] Markdown import (`remembra import-markdown`)
[ ] Backup (`remembra backup`)
[ ] Restore (`remembra restore`)
[ ] All 204 existing tests green against the SQLite backend
[ ] Dashboard smoke test passes (version badge, search, detail page)
```
