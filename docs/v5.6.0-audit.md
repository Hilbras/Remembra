# V5.6.0 Audit — Single-Host Assumptions

Roadmap §25–§30 (*Distributed Remembra*, renumbered from V5.2.0/V5.2.1) is the
next milestone. Before any of it is designed, this records what the shipped code
assumes about being the only process — because those assumptions are the work.
Audit T01 for this milestone; the previous milestone's equivalent is
[`v5.1.0-audit.md`](v5.1.0-audit.md).

Method: read the concurrency contract in `src/backend.ts` and check each mutating
path against it, then reproduce the interesting cases with two backend instances
over one database file. Findings marked **verified** were reproduced.

---

## S1 — verified: a cross-instance lost update

**Severity: high. Data loss, silent, with a success response.**

`src/backend.ts` states the contract:

> mutating calls must be safe under same-process concurrency (queueing) **and
> cross-process concurrency (advisory lock)** — a caller may issue `touch()`
> while another process runs `archive()`

`SqliteBackend` satisfies the first half only:

```ts
// src/sqlite-backend.ts:1086
private withLock<T>(fn: () => Promise<T>): Promise<T> {
  const prev = this.queue;          // this.queue is per-instance
  ...
}
```

It is a promise queue over one instance's `this.queue`. Two instances — two
processes, or one process with two backends — never interact. There is no
`BEGIN IMMEDIATE` and no `db.transaction()` anywhere in the file.

That is survivable for single-statement writes, because SQLite takes its own
write lock. It is **not** survivable for read-modify-write, and `update` is one:

```
SELECT rowid, version, ... WHERE id = ?     ← read
if (existingRow.version !== opts.expectedVersion) throw CONFLICT   ← checked in JS
UPDATE memories SET ..., version = ? WHERE id = ? AND <tenant>   ← no version predicate
```

The `WHERE` clause carries no version. The check happens in application code
*after* the read, so two writers that read the same version both pass it and both
write. Reproduced 5 times out of 5 with two instances over one `data.sqlite`:

```
A read version: 1 | B read version: 1
  A: wrote version 2 (written by A)
  B: wrote version 2 (written by B)
final content : written by B
final version : 2
>>> LOST UPDATE: 2 writers were each told they wrote version 2 and 2.
```

Both callers were told they succeeded. One write was discarded without any
error, so nothing above this layer could notice.

**Fixed.** The write is now a compare-and-swap on the version it read
(`AND version = ?`), and a zero-row result distinguishes `NOT_FOUND` (the row
went away) from `CONFLICT` (it moved on) — a caller must not retry a write whose
row no longer exists. Six tests in `src/test/sqlite-cas.test.ts` cover the race,
the error text, the delete-in-between case, and the two behaviours that must not
change: sequential writes with the correct version, and an update with no
`expectedVersion` at all.

This is the single most important finding to carry into §30. It was reachable
*before* any distributed work and would have become routine after it.

## S2 — verified: other mutators are read-modify-write without a CAS

`archive`, `forget`, `revive`, and `touch` all read and then write, with no
version predicate in the `WHERE` clause. Severity differs:

| Method | Risk under two instances |
|---|---|
| `archive` / `revive` | State transitions. Two instances can both observe "not archived" and both write; last writer wins, so the outcome is *a* valid state but not the one the loser was told about. |
| `forget` | **Was not safe — corrected after the first fix.** This row originally said the outcome was safe because deleting twice is idempotent. It is idempotent in *outcome* but not in *behaviour*: a sibling store instance could unlink the file between `findFile` and `unlink`, and the resulting `ENOENT` surfaced as an `IO_ERROR` to a caller that had done nothing wrong. It reproduced as an intermittent `foundation.test.ts` failure ("delete racing search never throws"). `ENOENT` on the unlink is now treated as the already-reported "missing" result. |
| `touch` | Benign. Both writers write an equivalent `last_seen`, so last-writer-wins loses nothing. |

None of these is a lost *content* update, so none is as severe as S1. All of them
are the same shape, and each needs its own decision about the right predicate
(a delete may not want one at all). The `forget` row was then disproved by a
pre-existing flaky test and fixed; `archive`, `revive`, and `touch` remain
deferred deliberately rather than changed blindly.

The `forget` failure is a useful correction to how this table was written. The
audit judged safety by *outcome* — deleting an already-deleted memory leaves the
right state — and missed that the *behaviour* a caller sees was an exception.
Idempotent state is not the same as a non-throwing call, and only the second one
keeps a racing caller from having to distinguish "someone else did it" from
"something went wrong".

## S3 — the health readiness cache is per server

`/health` and `/health/ready` cache their result for `REMEMBRA_HEALTH_CACHE_MS`
in a closure inside `createHttpServer`. That is correct per server and
irrelevant across servers: each instance probes its own storage. No change
needed; recorded so it is not mistaken for a shared cache later.

## S4 — in-process state that a multi-instance deployment would duplicate

Not defects today, because there is only ever one instance. They become
scheduling problems the moment there are N:

| State | Current home | N-instance consequence |
|---|---|---|
| Rate limiter | `InProcessRateLimiter` | per-instance budget, so an effective limit is N × configured |
| Quota | `QuotaRateLimiter` | same |
| Job queue | `JobQueue` in `src/job-queue.ts` | every instance runs its own copy of maintenance, decay, consolidation, and archiving |
| Decay / archive passes | in-process interval | duplicated work, and duplicated `touch`/archive races against S2 |
| Webhook drain | interval in `index.ts` | every instance drains the same durable queue |
| Parse cache | per-process | duplicated parse work only; benign |

The `RateLimiter` and quota interfaces already exist, which is why §26 can be an
adapter rather than a redesign. The job queue is the one that needs real design,
because §27's lease and attempt semantics have to be durable before N workers
can share it.

## S5 — durable state that is already shared, and whether it is safe to share

These already live on disk or in SQLite, so two instances pointed at the same
store would contend for them. Whether each is safe is a question for §30:

| State | Mechanism | Cross-instance safety |
|---|---|---|
| Batch idempotency ledger | SQLite ledger with an in-progress claim | designed for it — `CAS-001`-style claim semantics; needs a two-instance test |
| Webhook delivery store | durable SQLite queue | **unknown** — two drains could both claim the same delivery |
| Snapshot restore gate | marker file | **unknown** — two instances could both begin a restore |
| Recovery state | `.recovery-state.json`, atomic rename | **unknown** — two instances writing transitions could interleave |
| File-backend lock | PID lock file with staleness | correct for same-machine multi-process; not for separate hosts |
| SQLite backend writes | in-process queue only | S1, now fixed for `update` |

## S6 — the file backend's lock is same-machine only

`MemoryStore` takes a lock file containing the writer's pid, and treats it as
live while `process.kill(pid, 0)` succeeds. That is correct for several processes
on one host and **meaningless across hosts**: pid 1234 on another machine is not
this process, so the holder cannot be distinguished from a dead one. §26's
"Redis must not become a mandatory dependency" therefore has to hold for the
*lock* too, not just the cache — a multi-host deployment needs a lock that is not
a pid file, or the file backend is single-host by construction.

## What the milestone must not break

Every finding here is a property of the single-host contract that five releases
of hardening established. §30 asks for a guarantee that "distributed execution
does not weaken tenant isolation", and the concrete form of that is:

1. **Authentication still precedes every charge.** A shared limiter must not
   reintroduce the pre-auth exposure the bounded in-process limiter removed.
2. **Identities stay opaque.** The CAS predicate and any shared-state key must
   use the same truncated digests, never a raw principal.
3. **Every cross-instance decision is atomic**, in the sense S1 just
   demonstrated: check-then-act is not a decision.
4. **Optional means optional.** Redis absent must mean today's behaviour, not a
   degraded one. The Python SDK is stdlib-only and `better-sqlite3` is the only
   runtime dependency; a required Redis would break both the Node 18 gate and
   that property.
5. **Failures stay loud.** S1's real cost was not the lost write — it was that
   the loser was told it had succeeded.
