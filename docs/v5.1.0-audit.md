# V5.1.0 Infrastructure Audit

Scope: roadmap §18–§23 (rate limiting, quotas, health, metrics, logging,
shutdown) audited against the V5.4.0 tree before any V5.1 implementation, per
`tasks/v5.1-plan.md` T01.

Method: source audit of `src/rate-limiter.ts`, `src/http.ts`, `src/metrics.ts`,
`src/log.ts`, `src/index.ts`, and `src/service.ts`; label-value enumeration
across every `metrics.inc`/`metrics.observe` call site; a behavioural probe of
the limiter and of route ordering. Findings marked **verified** were reproduced
before being recorded.

Compatibility constraints that every finding below must respect:

- authentication still precedes any rate-limit consumption (SEC-RL-001),
- rate identity stays opaque — a truncated SHA-256, never a raw principal,
- quota dimensions are derived only from trusted host context, never from
  request JSON or an unverified header,
- health and metrics responses stay free of memory content, secrets, and
  provider diagnostics.

## Rate limiting

| # | Finding | Severity | Owner |
|---|---|---|---|
| R1 | **Unbounded limiter state.** Each distinct key allocates a window entry that is never evicted unless that same key is checked again after its window expires. | High | T02 |
| R2 | `check()` both decides and charges. There is no way to ask "would this be allowed?" without spending quota. | Medium | T02 |
| R3 | Not injectable: `http.ts:216` constructs `new RateLimiter(...)` inline, so V5.2 cannot supply Redis or a database without editing the request path. | High | T02 |
| R4 | One global limit and window for every key. No per-dimension policy, and no typed identity to attach one to. | Medium | T02/T03 |
| R5 | Pruning is `Math.random() < 0.001` — nondeterministic in a security-relevant path and effectively untestable. | Low | T02 |
| R6 | `clear()` is all-or-nothing and documented as test-only; there is no `reset(identity)`. | Low | T02 |
| R7 | The file header states `/metrics` is exempt from rate limiting. It is not. | High | T04 |

### R1 — verified: unbounded limiter state

`src/rate-limiter.ts:64-71` stores every checked key in `windows`, and the only
pruning path deletes entries whose timestamp list is *already empty*. An entry
becomes empty only when its own key is checked again after expiry, so any key
that is used once and abandoned is retained for the process lifetime.

```
$ node -e 'import {RateLimiter} from "./dist/rate-limiter.js";
  const rl=new RateLimiter({limit:5,windowMs:60000});
  for(let i=0;i<50000;i++) rl.check(`ip:rotating-${i}`);
  rl.check("ip:probe");
  console.log(rl.windows.size);'

distinct keys used      : 50000
window map size retained : 50001
```

Reachability: the anonymous bucket at `http.ts:352` is charged **before
authentication**, keyed by `requestAddress(req)`. An unauthenticated caller
rotating source addresses therefore grows process memory without ever holding
a credential, and no ceiling exists. Each retained entry holds a key string, an
object, an array, and a number.

Fix direction: a hard cap on tracked keys, a deterministic sweep of entries
whose newest timestamp is older than the window, and last-access ordering so
the cap evicts the least recently used rather than the oldest inserted.

### R7 — verified: `/metrics` is rate limited, and the code says otherwise

`rate-limiter.ts:7` claims `(/health, /metrics unkeyed, UI shell)` bypass the
check. Route order in `http.ts` disagrees:

```
320:  if (path === "/health")  → returns before auth and before the limiter
386:  const rateCheck = rateLimiter.check(rateKey);
539:  if (req.method === "GET" && path === "/metrics") → after the limiter
```

Operational consequence: a metrics scraper shares the application's bucket, so
under a rate-limit storm — the moment observability matters most — `/metrics`
returns `429` and the series go dark. The exempt-route contract has to be
enforced in one place, and the metrics route restored to it.

## Health

| # | Finding | Severity | Owner |
|---|---|---|---|
| H1 | Only `/health` exists; §20's `live`, `ready`, `storage`, and `provider` routes do not. | Medium | T04 |
| H2 | `/health` is unauthenticated, unrated, and **not cheap**. | High | T04 |

### H2 — verified by source

`/health` returns at `http.ts:320`, ahead of both authentication and rate
limiting, and calls `service.health()`. That method performs real work on every
call: `ensureRecoveryInitialized()`, `refreshDurableRecoveryState()`,
`await this.#backend.all()`, and `applyRecoveryEvent("ready")`, plus a durable
recovery-state write when a transition is required.

So an unauthenticated caller can drive storage reads and recovery-state writes
at request rate, with no limiter in front of the route. This is the opposite of
the plan's "keep liveness cheap and public", and it is the one finding here
that an unauthenticated remote party can reach directly.

Fix direction: a genuinely cheap `/health/live` that answers from process state
alone, and move the storage-touching and recovery-mutating work to
`/health/ready` behind authentication.

### Cardinality audit

Every label key at every call site was enumerated. All values are string
literals or booleans except one: `metrics.inc("remembra_jobs_total", { type:
job.type })` at `job-queue.ts:255`, with `job.type` typed
`JobType = "embed-memory" | … | (string & {})`.

All eleven internal `register`/`enqueue` call sites use literals, so no live
series is unbounded today. The exposure is the boundary: `register` accepts any
string, and V5.4 has just made Remembra a documented embeddable dependency, so a
host registering a per-tenant job type would silently create one series per
tenant in-process and in every scrape. Fix direction: bound the label to a
closed set, and document the closed set.

## Structured logging

| # | Finding | Severity | Owner |
|---|---|---|---|
| L1 | None of §22's standard fields are emitted: no `requestId`, `operation`, or `durationMs` on the request path. | Medium | T06 |
| L2 | The per-request id exists (`REQUEST_ID_HEADER`, `http.ts:261`) but is never attached to any log line, so one request cannot be followed across events. | Medium | T06 |
| L3 | Redaction is a field-name denylist plus value regexes. A raw query in a field whose name is not on the list is not redacted. | Medium | T06 |
| L4 | Tenant context is resolved per request but never logged at all, so multi-tenant debugging has no correlator. | Low | T06 |

The redactor itself is sound and centralized — `sanitizeLogValue` handles depth,
item count, cycles, and `Error` objects, and `isSensitiveField` normalizes
separators before matching. The gap is what is fed to it, not how it filters.

## Graceful shutdown

| # | Finding | Severity | Owner |
|---|---|---|---|
| S1 | Six-line shutdown that stops accepting and exits. It does not stop background jobs, the webhook drain interval, storage, or providers. | High | T07 |
| S2 | Timeout is a hardcoded 3s, not configurable, with no phase reporting. | Medium | T07 |
| S3 | No idempotency guard: a second `SIGTERM` re-enters the same closure while it is already draining. | Medium | T07 |
| S4 | Always `process.exit(0)`, so a forced timeout is indistinguishable from a clean stop. | Medium | T07 |
| S5 | **MCP mode installs no signal handlers at all.** | Medium | T07 |

### S1/S5 — verified by source

`index.ts:561-568`, inside the HTTP branch:

```ts
const shutdown = (sig: string) => {
  logEvent("info", "shutdown", { signal: sig }, `Remembra: received ${sig}, shutting down`);
  httpServer.close(() => process.exit(0));
  setTimeout(() => process.exit(0), 3000).unref();
};
process.on("SIGINT", () => shutdown("SIGINT"));
process.on("SIGTERM", () => shutdown("SIGTERM"));
```

`service.shutdownBackgroundJobs()` exists (`service.ts:569`) and
`startWebhookDrain()` is called immediately after (`index.ts:569`), but neither
is ever stopped. A process killed mid-drain leaves the interval running until
the exit, and queued webhook deliveries are never given their final attempt.
The `else` branch at `index.ts:570-574` starts MCP and registers no handlers,
so an MCP server takes the default `SIGTERM` disposition: immediate death, with
no drain and no recovery-state flush.

§23's sequence — stop accepting, finish active requests, stop workers, flush
logs, flush metrics, close providers, close storage, exit — currently has only
its first and last steps.

## Dependency boundaries to hold

- `RateLimiter`, quota accounting, health, and shutdown coordination must be
  **interfaces** with in-process implementations. Redis arrives in V5.2 and must
  not appear in V5.1 (plan risk row: premature Redis coupling).
- Health responses keep a public allowlist. `service.health()` already returns
  `errorLabel(err)` rather than an error message; that stays.
- Metrics labels stay low-cardinality by construction, not by convention — see M3.
- Shutdown phases must be idempotent and individually bounded, and must leave
  durable recovery state intact rather than forcing a clean `0` exit.
