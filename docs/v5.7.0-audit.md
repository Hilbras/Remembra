# V5.7.0 Retrieval Audit

Roadmap §31–§38, the **Advanced Retrieval Engine**. This audit reads the current
retrieval implementation against what the roadmap asks for, and records what is
missing, what is present but wrong, and what is present and sound.

Every finding below was reproduced against the built package. Two hypotheses of
mine were **wrong** and are corrected here rather than quietly dropped — see
[S2](#s2-the-idf-proxy-is-not-idf-but-it-does-not-invert-coverage) and the note
on MMR in [S4](#s4-deduplication-is-essentially-unimplemented).

## What is already sound

Worth stating before the gaps, because the milestone is additive and this code
should not be rewritten:

- **Query normalization** (`extractQuery`) handles temporal qualifiers
  (`latest`, `recent`, `before`, `after`) and empty-query browsing.
- **RRF fusion** (`rrfFuse`) handles tied scores by averaging rank, so positional
  bias does not compete with later modifier layers. That is the correct detail
  and it is easy to get wrong.
- **Trust gating** (`applyStandingGate`) keeps standing instructions behind a
  trust threshold rather than a score, which is the right shape for a security
  property.
- **Relation expansion** is restricted to already-authorized pool relations.
- **Evaluation harness** (`src/eval.ts`) computes precision@k, recall@k, MRR,
  nDCG@k, hit-rate@k, and latency at avg/p50/p95/p99. That is most of §38.
- **The reranker is genuinely optional.** `policy.reranking` is wired
  (`retrieval.ts:526`) and defaults to an identity reranker, so local/offline
  operation is preserved as §35 requires.

## S1 — Lexical matching is substring-only

**Roadmap §32** asks for exact matching, token matching, prefix matching, phrase
matching, weighted fields, and metadata filters.

`keywordScore` (`src/retrieval.ts:123`) does one thing:

```ts
const hay = (m.content + " " + m.tags.join(" ")).toLowerCase();
for (const t of terms) if (hay.includes(t)) hits++;
```

That is a substring test. Consequences, each reproduced:

| Case | Query | Result |
|---|---|---|
| **Substring false positive** | `cat` vs `"concatenate the streams"` | **60.00** — identical to a real match. Note this is a *mid-word* collision, not a prefix one: `"concatenate".startsWith("cat")` is false, the letters sit at index 3. The correct fixed score is 0. |
| Real match | `cat` vs `"the cat sat"` | 60.00 |
| **Phrase, correct order** | `red car` vs `"the red car"` | 60.00 |
| **Phrase, reversed** | `red car` vs `"car the red"` | 60.00 — order is not scored |
| **No phrase at all** | `red car` vs `"a red dog here"` | 30.00 — scores anyway |
| **Field weight** | term in `content` vs in `tags` | 60.00 vs 60.00 — **identical** |

There is no `title` field on `Memory`; the searchable fields are `content` and
`tags`. (An earlier draft of this audit said "content, tags, and title" — `title`
does not exist, and the fix is scoped to the two real fields.)

So a document that contains the letters `cat` inside another word ranks exactly
as high as one containing the word `cat`. There is no token boundary, no phrase
scoring, and `content` and `tags` are concatenated with no weight — a tag
mention is worth exactly as much as prose.

**Severity: high.** This is the default path. It affects every deployment that
does not enable embeddings, which is the documented default
(`REMEMBRA_EMBEDDINGS=none`), and it affects lexical scoring *within* hybrid
retrieval too, since `rrfFuse` consumes this ranking.

## S2 — The idf proxy is not idf, but it does not invert coverage

`keywordScore` computes:

```ts
const idf = Math.log(1 + totalDocs / Math.max(1, hits));
return Math.min(60, tfRatio * 60 * (0.5 + 0.5 * Math.min(1, idf)));
```

`hits` is **this document's** match count, so this is a function of the document's
own query coverage, not of how rare a term is across the corpus. Real IDF needs
corpus term frequencies; this has neither.

**I predicted this would invert**, reasoning that fewer hits means a larger
multiplier and therefore a higher score for a worse match. **That is wrong**, and
the measurement says so:

```
doc matching all 4 terms:  60.00
doc matching 1 of 4 terms:  15.00
```

Coverage ordering is correct. The defect is narrower than I first thought: the
term is not IDF, it is a coverage discount, and because it is derived from the
document rather than the corpus it cannot distinguish a rare term from a common
one. Two documents covering the same fraction of the query score identically
regardless of whether the shared term is common or rare.

**Severity: medium, not high — and the T03 work confirmed that.** A real
substitute arrived, not a layer on top: the scorer's `totalDocs` parameter is gone,
`buildTermStatistics` counts document frequencies over the candidate set using the
backend's true corpus total, and each term's credit is scaled by a normalised IDF
in (0, 1]. T03-003 and T03-004 pin the coverage ordering that *was* correct, so the
replacement did not trade one ranking bug for another.

Two things worth recording from the implementation. **Normalising** IDF against
`log(1 + documentCount)` is what keeps the coverage denominator fixed — a raw IDF
would rescale every score by whichever term happened to be rarest, quietly
re-breaking the phrase and field work T02 did. And a term with **no recorded
frequency is treated as appearing in every document**, because assuming a term is
rare when it is actually common is how a stopword ends up dominating a result set;
T03-006 pins that it is discounted rather than credited.

One consequence, found by a test: a term appearing in exactly **one** document is
maximally rare at *any* corpus size, so `totalDocs` cannot change a df=1 term's
weight. The corpus total only moves terms with df ≥ 2. That is inherent to
normalised rarity, not a defect, and T03-015 uses a df=5 term because a df=1 term
demonstrated nothing.

## S3 — Hybrid weights are not configurable

**Roadmap §34** is explicit: *"Weights must be configurable."*

`RetrievalPolicyOptions` (`src/retrieval.ts:25`) carries four booleans —
`requireRoleTrust`, `diversity`, `reranking`, `relationExpansion` — and **no
numeric weights**. `rrfFuse` hardcodes `RRF_K = 1.6`. The components §34 names
(lexical, semantic, metadata, recency, confidence) are all applied, but their
relative influence is fixed in code and cannot be tuned per deployment.

**Severity: medium.** Not a security property, but it is a stated requirement
and it is the difference between a retrieval engine an operator can adapt and one
they cannot.

## S4 — Deduplication is essentially unimplemented

**Roadmap §36** requires detection of four kinds: exact duplicates, near
duplicates, same-source duplicates, and superseded memories — while explicitly
*not* destroying historical records.

What exists is `mmrDedup` (`src/retrieval.ts:342`), which is **Maximal Marginal
Relevance: a diversity reordering, not duplicate detection.** It never classifies
anything as a duplicate. Reproduced:

```
identical text, identical embeddings, limit 3 of 3 candidates
  lambda=0.5 -> kept 3 of 3 (ids a,b,c)
  lambda=0.9 -> kept 3 of 3 (ids a,b,c)
```

MMR only drops candidates when the pool exceeds the limit, and it reorders by
similarity to *already-selected* items — so the first item is always kept and an
exact duplicate is only penalised relative to selection order.

More decisively, two of the four required detectors have **no code path at all**:

- **Exact duplicates** — no content hash or normalized-text comparison.
- **Same-source duplicates** — no `source` grouping anywhere in the tree.
- **Superseded memories** — `supersededBy` exists on the type
  (`src/types.ts:182`) and is written by consolidation, but **no retrieval path
  ever consults it**. Reproduced: a candidate with `supersededBy: "new"` survives
  retrieval alongside the memory that supersedes it, so a query for a policy
  returns both v1 and v2.
- **Near duplicates** — the only thing `mmrDedup` approximates, and only when a
  query vector exists.

And in the **default configuration** (`REMEMBRA_EMBEDDINGS=none`) it is a pure
pass-through:

```
no query vector -> kept 3 of 3 (pure pass-through)
```

**Severity: high.** Returning v1 and v2 of a superseded policy is the kind of
result that makes a memory system untrustworthy, and it happens in the default
mode.

## S5 — The context budget is missing two of four dimensions

**Roadmap §37** requires `maxTokens`, `maxItems`, `maxBytes`, `maxLatency`.

| Dimension | Status |
|---|---|
| `maxItems` | present (`limit`) |
| `maxTokens` | present (`retrieval.ts`, `context.ts`) |
| `maxBytes` | **absent from the retrieval path** — it exists in `service.ts` and `http.ts` for request bodies, which is a different budget |
| `maxLatency` | **absent from the entire tree** |

There is also no unified budget object: the limit and the token cap are
independent parameters threaded separately, so a caller cannot express "fit this
into 8k tokens **and** 16KB **and** answer in 200ms".

**Severity: medium.** `maxLatency` is the interesting one — a retrieval budget
that cannot express a deadline cannot degrade gracefully under load, which is the
behaviour §37 is really asking for.

## S6 — Two of seven required evaluation metrics are missing

**Roadmap §38** lists precision, recall, MRR, nDCG, latency, **token efficiency**,
and **duplicate rate**.

`src/eval.ts` computes the first five (plus hit-rate and latency percentiles).
Missing:

- **Token efficiency** — tokens returned per token of context budget consumed.
  Without it there is no way to tell whether a retrieval change made the context
  *more* or *less* dense with signal.
- **Duplicate rate** — the fraction of returned results that are duplicates. This
  is the metric that would have caught **S4** automatically, and §38's rule that
  *"every retrieval-engine change must run against the benchmark set"* cannot
  enforce a property nothing measures.

**Severity: high for duplicate rate**, because it is the guardrail for S4. Medium
for token efficiency.

## Sequencing

The order matters, and it is not the roadmap's:

1. **S6-duplicate-rate first.** It is cheap, and it is the measurement that makes
   S4 verifiable. Building the detector before the metric means shipping a
   dedup change with no way to show it helped.
2. **S1 next.** It is the default path, it has the worst false-positive shape, and
   S2's fix (real corpus statistics) has to change the same function's signature.
   Doing them together avoids touching `keywordScore` twice.
3. **S4 detectors.** Exact and same-source are cheap and deterministic;
   superseded-memory suppression needs a decision about *when* a superseded copy
   is still useful (audit trail, historical questions) that should be settled
   before code.
4. **S5, S3.** Independent of the above; `maxLatency` is the substantive part.
5. **S38's regression-query rule** last, once the metrics exist to gate it.

## Open questions for the plan

- **Should a superseded memory be suppressed by default?** §36 says do not
  *destroy* historical records, which is about storage, not retrieval. But
  returning v1 when v2 supersedes it is usually wrong. I would suppress it by
  default and keep it reachable through an explicit `includeSuperseded` flag, and
  I would want that confirmed rather than assumed.
- **Does §32's "metadata filters" mean filters inside the lexical scorer, or the
  existing `scope`/`type` filters promoted into a declared filter object?** The
  roadmap lists it under lexical retrieval, which suggests the former, but the
  existing filter surface already covers most of the latter.
- **What is the intended `maxLatency` behaviour when exceeded** — return the best
  results found so far, or fail? Returning partial results is almost certainly
  right for a memory system, but it needs to be a stated decision.

## S7 — Non-ASCII queries are silently dropped (found while building the T08 gate)

`tokenize` has a CJK branch that splits a run of CJK characters into individual
characters, so a CJK document's *content* is indexed sensibly. But the query terms
the pipeline actually uses come from `extractQuery`, and its filter is ASCII-only:

```ts
const terms = body
  .toLowerCase()
  .split(/\s+/)
  .filter((t) => t.length > 1 && /^[a-z0-9]+$/u.test(t));
```

Reproduction:

```
extractQuery("deployment pipeline") -> ["deployment","pipeline"]
extractQuery("记录回滚")             -> []
extractQuery("记录 回滚")            -> []
extractQuery("デプロイ")             -> []
```

So a query in any non-ASCII script produces **zero** terms, no keyword list is
built, and retrieval falls back to the vector path alone — which is nothing at all
when a deployment has no embedding provider. The user gets an empty result set,
not an error and not a degraded result.

Two consequences worth stating separately:

- The CJK branch in `tokenize` is **unreachable from the query path**. It only
  runs over document content, and only when the query terms it is filtering
  against are already ASCII. It looks like support and is not.
- `CJK_RANGE` also does not match katakana, so even fixing the `extractQuery`
  filter would not make Japanese katakana queries work. Both need attention
  together, not one at a time.

**Not fixed here.** The one-line change to the filter is a behaviour change on a
public surface: today every non-ASCII query returns nothing lexical, and after it
those queries start matching. That is a fix, but it is also a change in what
existing deployments get back for non-ASCII input, so it wants a decision and a
changelog entry rather than arriving inside a different task.

It is also why the benchmark set has no CJK scenario. A gate that fails on
correct code is not a gate, and adding one would have meant either shipping a
failing release stage or quietly weakening the set to hide a real bug.

The fix is small and should be its own task: replace the ASCII filter with the
character class `tokenize` already uses, widen `CJK_RANGE` to the ranges
`Intl.Segmenter` or a proper Unicode script property covers, and re-check the
benchmark metrics — CJK documents would then enter the lexical path and the
ranking numbers would legitimately shift.
