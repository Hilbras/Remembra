## Compatibility with V5.5.1

### Preserved contracts

- **No new runtime dependency.** Still four: `@modelcontextprotocol/sdk`,
  `better-sqlite3`, `yaml`, `zod`. `redis` is an **optional peer** and is not
  even a devDependency.
- **A single-process deployment is unchanged.** With no `REMEMBRA_REDIS_URL`,
  no Redis code is imported, no shared store is opened, no job ledger is
  touched, and `/health/ready` is **byte-identical** to 5.5.1 — it does not even
  gain a field saying "absent". `SHARED-002` asserts the payload's key set.
- **The no-subcommand CLI path is unchanged** and still requires no
  configuration. `ROLE-007` runs the real CLI to prove it.
- `JobQueue`, the in-memory promise-based queue, is untouched and remains what a
  single process uses.
- `InProcessRateLimiter` and `QuotaRateLimiter` are unchanged. The shared
  limiter *replaces* the in-process one wholesale when configured; it does not
  compose with it, and a mixed configuration is not reachable.
- `MemoryService.health()` keeps its exact shape. The shared-state view is added
  by the HTTP layer, and only when configured.

### New behaviour that is opt-in

- `REMEMBRA_REDIS_URL` set but unreachable is a **startup failure**. There is no
  silent fallback to per-instance state.
- A store that becomes unreachable *after* startup makes the limiter **fail
  closed** (503) rather than degrade, and readiness reports `unready`. It
  recovers on its own at the next successful operation.
- `remembra worker --http` and `remembra worker --port N` are startup errors.
- A role process without an HTTP surface refuses data verbs (`remembra worker
  export`) rather than ignoring them.

### Additive HTTP surface

- `GET /api/v1/capabilities` gains `distributed`. It is present whether or not
  shared state is configured, because the manifest describes the **build** —
  the same reasoning that has always applied to `webhooks`.
- `GET /health/ready` and `GET /health` gain an optional `shared` object
  (`{ mode, error? }`) **only when `REMEMBRA_REDIS_URL` is set**. It carries a
  classified label only: never the URL, host, port, or password.

## Defects found and fixed

- **A cross-instance lost update on the SQLite backend.** `update` was not a
  compare-and-swap: two instances both read version *N* and both were told they
  had written version *N+1*, and one change silently vanished. Reproduced 5/5.
  The update is now a single `UPDATE … WHERE … AND version = ?` statement, and
  `NOT_FOUND` is distinguished from `CONFLICT`.
- **A spurious `IO_ERROR` from a racing delete** on the file backend: `forget`
  surfaced `ENOENT` when a concurrent delete removed the file between `findFile`
  and `unlink`. A missing file is now idempotent, which is a different property
  from "does not throw".
- **A cold-start race in the batch idempotency ledger.** Two processes starting
  together could observe each other's not-yet-`0600` `claims.sqlite` — created by
  better-sqlite3 with the process umask and only `chmod`ed after the open — and
  one would refuse to start. The file is now created `0600` with
  `O_CREAT|O_EXCL` before it is opened. The permission check is unchanged.

## What is deliberately not claimed

- **No live Redis was exercised.** There is no Redis in this project's test
  environment. The quota and lock scripts are verified by executing the *actual
  text shipped in `src/redis.ts`* through a Lua 5.3 VM with a shim of the Redis
  commands they use (28 checks) — that covers their logic, not a real server.
  The failure matrix's outage rows verify *our* response to a store outage, not
  Redis. Unverified: that the scripts load under a real Lua sandbox, a real
  network partition rather than a client that throws, Redis restart with
  in-flight commands, and `EVALSHA`/script-cache behaviour. Closing this needs a
  Redis instance in CI.
- **The service's own periodic tasks are still per-instance.** Maintenance
  reaches the shared ledger through the `scheduler`/`worker` roles, but the
  service's internal decay timer still runs in every process. The ledger stops
  duplication for work routed through it; it does not yet own every periodic
  task. See the limitations in [lock and jobs](lock.md).
- **Cross-*host* exclusion** depends on Redis being configured. Single-host file
  locking is authoritative for one machine only, which is stated in
  [lock and jobs](lock.md).
